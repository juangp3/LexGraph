# Phase 8 — Knowledge Graph Expansion Specification

## 1. Overview

### Goal

Expand LexGraph from an **etymology graph** into a broader **linguistic knowledge graph**.

Phase 7 makes graph retrieval fast, safe, and scalable.

Phase 8 defines **what the graph should contain and how users can explore it**.

The key distinction is:

> **Phase 7 optimizes the graph infrastructure. Phase 8 expands the knowledge represented by the graph.**

The graph should evolve from:

```text
word
  ↓
ancestor
  ↓
ancestor
```

into:

```text
                         Language Family
                               │
                         Language
                               │
                    ┌──────────┴──────────┐
                    │                     │
                  Word                  Word
                    │                     │
          ┌─────────┼─────────┐           │
          ▼         ▼         ▼           ▼
       Meaning   Etymology  Cognate     Variant
          │         │         │
          ▼         ▼         ▼
       Concept   Ancestor   Related Word
```

This phase should make LexGraph significantly more useful as a **linguistic exploration platform**, rather than only an etymology viewer.

---

# 2. Strategic Objective

The expanded knowledge graph should allow users to answer questions such as:

> Where does this word come from?

> What other words share its ancestor?

> Which languages inherited this root?

> Is this word a cognate of another word?

> What language family does it belong to?

> How did its meaning change?

> Which modern languages contain descendants of the same ancestral form?

> Is the similarity due to inheritance, borrowing, or coincidence?

The last question is particularly important.

LexGraph must distinguish **different kinds of linguistic relationships** rather than treating every connection as evidence of common ancestry.

---

# 3. Core Design Principle

Every graph connection must have a semantic meaning.

Avoid:

```text
A ─── related ─── B
```

Prefer:

```text
A ──COGNATE_WITH── B

A ──BORROWED_FROM── B

A ──INHERITED_FROM── B

A ──DERIVED_FROM── B

A ──VARIANT_OF── B

A ──HAS_SENSE── B
```

This is fundamental to the credibility of LexGraph.

---

# 4. Knowledge Graph Scope

Phase 8 should introduce or formalize the following entity categories.

### Core

1. Word
2. Lexeme
3. Language
4. Language Family
5. Meaning / Sense
6. Root / Proto-form
7. Historical Form

### Relationships

8. Cognate
9. Borrowing
10. Derivation
11. Inheritance
12. Semantic relationship
13. Variant relationship

### Supporting entities

14. Source
15. Historical period
16. Region
17. Script

Not all of these need a dedicated database table immediately.

The architecture should distinguish **entity type** from **storage implementation**.

---

# 5. Entity Model

Recommended conceptual hierarchy:

```text
Entity
├── Word
├── Lexeme
├── Language
├── LanguageFamily
├── Root
├── Meaning
├── HistoricalForm
├── Region
├── Script
└── Source
```

Relationships connect entities.

---

# 6. Word Entity

Example:

```json
{
  "id": "uuid",
  "type": "word",
  "text": "father",
  "languageId": "uuid"
}
```

A Word represents an attested linguistic form.

---

# 7. Lexeme Entity

Where the data supports it, distinguish:

```text
orthographic form
        ↓
lexeme
        ↓
senses
```

Example:

```text
father
   │
   ▼
LEXEME: father
   │
   ├── male parent
   ├── male ancestor
   └── founder
```

This distinction prevents different meanings of the same spelling from being incorrectly merged.

---

# 8. Language Entity

Example:

```text
English
```

Metadata:

```text
id
name
ISO code
family
branch
script
historical status
```

---

# 9. Language Family Entity

Example:

```text
Indo-European
```

Hierarchy:

```text
Indo-European
   │
   └── Germanic
         │
         ├── West Germanic
         │      ├── English
         │      ├── Dutch
         │      └── German
         │
         └── North Germanic
                ├── Swedish
                └── Danish
```

This should eventually become independently explorable.

---

# 10. Root / Proto-form

A reconstructed form should be represented separately from ordinary words.

Example:

```text
*ph₂tḗr
```

Metadata:

```text
type: reconstructed
language: Proto-Indo-European
attestation: reconstructed
confidence: ...
```

The `*` notation should not be the only indicator.

The data model must explicitly identify reconstructed entities.

---

# 11. Historical Form

Example:

```text
fæder
```

Metadata:

```text
language: Old English
period: Old English
attested: true
```

This distinguishes:

```text
*fadēr
```

from:

```text
fæder
```

---

# 12. Meaning / Sense

Meanings should be separate entities where the underlying data supports that.

Example:

```text
father
   │
   ├── Sense 1
   │      "male parent"
   │
   └── Sense 2
          "founder"
```

This enables future semantic evolution.

---

# 13. Source Entity

Sources should become first-class provenance entities.

Example:

```text
Wiktionary
Glottolog
DBnary
```

A source can be attached to:

* entity
* relationship
* meaning
* pronunciation
* etymology
* language classification

---

# 14. Relationship Model

A relationship should contain more than:

```json
{
  "source": "A",
  "target": "B"
}
```

Recommended:

```json
{
  "id": "uuid",
  "source": "A",
  "target": "B",
  "type": "INHERITED_FROM",
  "confidence": 0.94,
  "sources": [],
  "evidence": {},
  "metadata": {}
}
```

---

# 15. Relationship Types

Initial canonical vocabulary:

```text
INHERITED_FROM
BORROWED_FROM
DERIVED_FROM
COGNATE_WITH
VARIANT_OF
HAS_SENSE
BELONGS_TO_LANGUAGE
BELONGS_TO_FAMILY
DESCENDANT_OF
RELATED_TO
```

Avoid adding dozens of relationship types prematurely.

---

# 16. Inheritance

Represents historical linguistic descent.

```text
English father
      │
      ▼
Old English fæder
```

Relationship:

```text
INHERITED_FROM
```

This should be directional.

---

# 17. Borrowing

Represents lexical borrowing between languages.

Example:

```text
English algebra
       │
       ▼
Arabic al-jabr
```

Relationship:

```text
BORROWED_FROM
```

This must **not** be represented as ordinary inheritance.

---

# 18. Cognates

Cognates represent words/forms with a common ancestral origin.

Example:

```text
English father
German Vater
Dutch vader
```

Possible model:

```text
father ──COGNATE_WITH── Vater
father ──COGNATE_WITH── vader
```

But the underlying evidence should ideally connect all of them to the common ancestor:

```text
              *ph₂tḗr
              /  |  \
             /   |   \
        father  Vater vader
```

This is preferable to relying exclusively on pairwise cognate edges.

---

# 19. Derivation

Example:

```text
father
   │
   ▼
fatherhood
```

Relationship:

```text
DERIVED_FROM
```

This is synchronically/morphologically different from historical inheritance.

---

# 20. Variant

Example:

```text
color
colour
```

Relationship:

```text
VARIANT_OF
```

Variants should not automatically imply:

```text
different etymological origin
```

---

# 21. Semantic Relationship

Example:

```text
father
   │
   ├── related to ── mother
   ├── related to ── parent
   └── related to ── child
```

These should not appear in the etymological lineage by default.

They belong to a separate semantic layer.

---

# 22. Layered Graph Architecture

This is one of the most important design decisions.

LexGraph should conceptually contain multiple graph layers.

```text
                 LEXGRAPH
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
 Etymological   Linguistic    Semantic
    Layer         Layer         Layer
       │            │            │
 ancestry        language       meaning
 borrowing       morphology     concepts
 cognates        variants       relations
```

The UI can combine them, but the backend should know which layer a relationship belongs to.

---

# 23. Graph Layers

Recommended initial layers:

### Etymology

```text
INHERITED_FROM
BORROWED_FROM
COGNATE_WITH
```

### Morphology

```text
DERIVED_FROM
VARIANT_OF
```

### Language

```text
BELONGS_TO_LANGUAGE
BELONGS_TO_FAMILY
```

### Semantics

```text
HAS_SENSE
RELATED_TO
```

---

# 24. Why Layers Matter

Without layers, a graph becomes:

```text
father
 ├── fæder
 ├── parent
 ├── German
 ├── family
 ├── fatherhood
 └── Vater
```

The user cannot understand why these things are connected.

With layers:

```text
Etymology
father → fæder → *fadēr

Cognates
father ↔ Vater ↔ vader

Morphology
father → fatherhood

Semantics
father → parent → family
```

Much clearer.

Phase 7 provides the infrastructure.

Every expansion should request only the relevant relationship layer.

Example:

```http

    relationshipTypes=COGNATE_WITH&
    depth=1
```

# 30. Expansion Limits

Never automatically expand everything.

Default:

```text

```

User explicitly chooses deeper exploration.

# 32. Language Graph

Users should eventually be able to explore:

```text
English
   │
   ▼
West Germanic
   │
   ▼
Germanic
   │
   ▼
Indo-European
```

This is not an etymological word lineage.

It is a **language classification hierarchy**.

# 33. Language Family Navigation

Clicking:

```text
Germanic
```

should allow:

```text
Explore Germanic
```

and show:

```text
Germanic
├── West Germanic
├── North Germanic
└── East Germanic
```

where the dataset supports the classification.

---

# 34. Language Family as Graph

The graph can represent:

```text
Family
 ↓
Branch
 ↓
Subgroup
 ↓
Language
```

This makes language classification itself explorable.

---

# 35. Language Relationship Confidence

Historical language classifications can sometimes be debated.

Do not encode every classification as absolute truth.

Support:

```text
confidence
sources
classification status
```

---

# 36. Borrowing Network

LexGraph should support exploration of lexical borrowing.

Example:

```text
Arabic
   ↓
Spanish
   ↓
English
```

A user could ask:

```text
How did this word reach English?
```

The graph can show the chain where evidence supports it.

---

# 37. Borrowing vs Inheritance

The UI and API must clearly distinguish:

```text
Inherited
```

from:

```text
Borrowed
```

This distinction is a major linguistic feature.

---

# 38. Cognate Network

A root should become a hub.

Example:

```text
             Proto-root
            /    |     \
           /     |      \
       English German   Dutch
       father  Vater    vader
```

Users should be able to explore the modern descendants.

---

# 39. Root-Centric Exploration

Clicking:

```text
*ph₂tḗr
```

should offer:

```text
Explore descendants
```

Potential graph:

```text
*ph₂tḗr
 │
 ├── Proto-Germanic
 │       │
 │       ├── English father
 │       ├── German Vater
 │       └── Dutch vader
 │
 └── Other descendants
```

---

# 40. Semantic Layer

The semantic graph should eventually allow:

```text
father
   │
   ▼
parent
   │
   ▼
family
```

But this layer should be visually and conceptually separate from etymology.

---

# 41. Semantic Evolution

Where historical meaning data exists:

```text
Old meaning
      ↓
Intermediate meaning
      ↓
Modern meaning
```

Example:

```text
meaning A
    ↓
meaning B
    ↓
meaning C
```

Each transition must have evidence.

---

# 42. Semantic Similarity

Do not automatically interpret semantic similarity as historical relationship.

For example:

```text
father
parent
```

being semantically related does not mean:

```text
father ← parent
```

The relationship must have explicit semantics.

---

# 43. Morphological Network

Support:

```text
nation
   │
   ├── national
   ├── nationality
   ├── nationalize
   └── international
```

This creates a second exploration dimension.

---

# 44. Morphological vs Etymological Derivation

Do not conflate:

```text
historical ancestor
```

with:

```text
modern morphological derivative
```

Example:

```text
nation → national
```

is not equivalent to:

```text
English → Old English
```

---

# 45. Word Family

The UI can provide a "Word Family" view:

```text
              nation
           /     |      \
     national  nations  nationality
```

This should use explicit derivational evidence.

---

# 46. Historical Timeline Graph

Where historical periods are available:

```text
Proto-form
   ↓
Ancient form
   ↓
Medieval form
   ↓
Modern form
```

This can become a temporal graph.

---

# 47. Temporal Metadata

Entities may include:

```text
firstAttested
lastAttested
period
dateRange
```

Do not assume exact dates where only approximate periods are available.

---

# 48. Geographic Layer

Future-ready support:

```text
word
 ↓
language
 ↓
region
```

Potentially:

```text
Latin
 ↓
Romance
 ↓
Iberian Peninsula
```

But geographic claims require strong source support.

---

# 49. Script Layer

Words may be connected to scripts.

Example:

```text
language
 ↓
Latin script
```

Potential future exploration:

```text
How was this word historically written?
```

---

# 50. Source Graph

Sources should not merely appear as text.

Conceptually:

```text
Word
 │
 ├── supported by → Source A
 ├── supported by → Source B
 └── contradicted by → Source C
```

However, this should be surfaced selectively in the UI.

The user should not normally see a huge source graph.

---

# 51. Evidence Graph

A major long-term architectural principle:

```text
Fact
 │
 ├── source
 ├── confidence
 ├── evidence
 └── date
```

Instead of treating the graph as unquestionable truth.

This is particularly important for reconstructed or disputed etymologies.

---

# 52. Confidence Model

Confidence should belong to **relationships/facts**, not simply entities.

Bad:

```text
father confidence = 95%
```

Better:

```text
father
  └── INHERITED_FROM → fæder
      confidence = 95%
```

Another relationship could have:

```text
father
  └── relationship → X
      confidence = 61%
```

---

# 53. Competing Hypotheses

The graph must be capable of representing:

```text
Word
 ├── hypothesis A
 └── hypothesis B
```

without pretending that one is universally accepted.

---

# 54. Relationship Provenance

Every significant relationship should be able to answer:

```text
Who says this?
What source?
Which version?
How confident?
What evidence?
```

This is critical for scholarly credibility.

---

# 55. Source Agreement

Potential metadata:

```text
sourceCount
supportingSources
contradictingSources
```

Example:

```text
Supported by 4 sources
Disputed by 1 source
```

---

# 56. Graph Quality Score

Potential future concept:

```text
Graph quality
★★★★☆
```

But avoid creating an arbitrary single score too early.

Prefer transparent components:

```text
Source coverage
Relationship confidence
Source agreement
```

---

# 57. Data Quality Rules

Phase 8 must introduce validation rules.

Examples:

### Invalid

```text
word → INHERITED_FROM → same word
```

### Suspicious

```text
word in English
INHERITED_FROM
word in Japanese
```

unless explicitly supported by historical data.

---

# 58. Relationship Direction Validation

Rules should verify:

```text
INHERITED_FROM
```

points toward an older form.

Where dates are known:

```text
modern
  ↓
historical
```

should be valid.

Reverse should trigger validation.

---

# 59. Language Validation

A word should normally belong to a language.

```text
father
BELONGS_TO_LANGUAGE
English
```

If language is unknown:

```text
language = unknown
```

rather than inventing one.

---

# 60. Root Validation

Reconstructed roots should have:

```text
reconstructed = true
```

and ideally:

```text
language = Proto-Indo-European
```

---

# 61. Graph Integrity

Create validation jobs to detect:

* orphan nodes
* orphan relationships
* invalid references
* cycles where forbidden
* duplicate edges
* contradictory metadata
* impossible language assignments

---

# 62. Duplicate Relationships

Avoid:

```text
A → B
A → B
A → B
```

unless each edge represents a genuinely different sourced assertion.

Prefer one canonical relationship with multiple provenance records.

---

# 63. Relationship Identity

A relationship should have its own ID.

Example:

```json
{
  "id": "relationship-123",
  "type": "COGNATE_WITH",
  "source": "word-a",
  "target": "word-b"
}
```

This enables:

* provenance
* confidence
* editing later
* auditing

---

# 64. Graph Expansion API

Phase 8 should build on Phase 7's API.

Recommended:

```http
GET /v1/graph/{entityId}/expand
```

Parameters:

```text
direction
relationshipTypes
entityTypes
depth
limit
cursor
```

Example:

```http
GET /v1/graph/123/expand?
    direction=ancestors&
    relationshipTypes=INHERITED_FROM&
    depth=2
```

---

# 65. Multi-Layer Expansion

Example:

```http
GET /v1/graph/123/expand?
    relationshipTypes=COGNATE_WITH,BORROWED_FROM
```

Response should retain relationship types.

The frontend decides how to display them.

---

# 66. Graph Context

Every response should identify the context:

```json
{
  "meta": {
    "root": "123",

      "direction": "ancestors",
```

# 71. Preventing Graph Explosion

A knowledge graph can become unusable if everything connects to everything.

Avoid default:

```text
father
 ├── parent
 ├── mother
 ├── family
 ├── male
 ├── human
 ├── English
 ├── Germanic
 ├── German
 ├── Dutch
 ├── fatherhood
 ├── ...
```

Instead:

```text
father
 └── etymology
       └── ...
```

Users explicitly expand additional layers.

# 80. Linguistic Family Exploration

```text

```

as a starting node.


# 81. Family → Words

A family node can eventually answer:

> Show interesting words from this family.

But this should not load thousands of words automatically.

Use search, sampling, ranking, or explicit exploration.

---

# 82. Graph Sampling

When a node has thousands of relationships:

```text
Germanic
 └── 5000+ words
```

do not render all nodes.

Return:

```text
top N
```

plus:

```text
remainingCount
```

Example:

```json
{
  "nodes": [],
  "meta": {
    "totalAvailable": 5342,
    "returned": 100,
    "truncated": true
  }
}
```

---

# 83. Ranking Graph Relationships

Where multiple relationships exist, ranking can consider:

* confidence
* source count
* relevance
* relationship type
* language proximity
* historical relevance

But ranking must not alter the underlying truth.

It only determines display order.

---

# 84. Graph Relevance

Example:

For English `father`, prioritize:

```text
Old English
Proto-Germanic
Proto-Indo-European
```

over unrelated semantic associations.

---

# 85. Graph Provenance View

Advanced users should be able to click an edge:

```text

```

and see:

```text
Relationship

Inherited from
```

---

# 86. Historical Evidence

Where available, support:

```text
first attestation
earliest known form
historical spelling
source citation
```

Do not imply that "earliest record found" equals "origin".

---

# 87. Uncertainty Representation

The graph should support:

```text
certain
probable
possible
disputed
unknown
```

This is preferable to forcing everything into a numeric confidence value.

---

# 88. Confidence + Status

Recommended:

```json
{
  "confidence": 0.87,
  "status": "PROBABLE"
}
```

This gives both machine-readable and human-readable representations.

---

# 89. Evidence Model

A relationship can have multiple evidence items:

```json
{
  "evidence": [
    {
      "sourceId": "...",
      "type": "DICTIONARY_ENTRY",
      "reference": "...",
      "supports": true
    }
  ]
}
```

This makes the graph auditable.

---

# 90. Data Import Compatibility

Phase 8 must integrate with Phase 4's ingestion system.

New entity types and relationships should enter the graph through the same controlled pipeline.

Do not manually insert production graph records from the frontend.

---

# 91. Canonicalization

Before adding an entity:

```text
normalize
    ↓
identify language
    ↓
identify entity
    ↓

    ↓

    ↓
```

# 92. Entity Resolution

Potential duplicate:

```text
English father
English Father
father
```

should resolve to the same canonical entity where appropriate.

But:

```text
English father
German Vater
```

must remain distinct.

---

# 93. Historical Identity

Historical forms must not automatically merge with modern forms.

Example:

```text
father

```

are separate entities connected by:

```text

```

---

# 94. Reconstructed Identity

Likewise:

```text
*fadēr
```

is a separate entity.

The graph relationship carries the interpretation.

---

# 95. Dataset Versioning

Graph facts should be associated with dataset version where appropriate.

Example:

```text
datasetVersion: 42
```

This allows future reprocessing.

# 96. Graph Evolution

The architecture must support:

```text
Dataset v41
     ↓

```

without corrupting relationships.

Ideally, the canonical database represents the current dataset while ingestion history remains auditable.

# 97. Backward Compatibility

# 103. Entity Metadata

Entity-specific metadata should not turn the main entity table into an unstructured dumping ground.

Use structured columns for important searchable attributes.

Potentially:


# 104. Avoid Over-Generalization

A generic graph model is useful.

But avoid turning everything into:

```text
entity
entity
relationship
```

with no domain constraints.

LexGraph needs linguistic semantics.

The graph engine can be generic; the **domain model must not be generic to the point of meaninglessness**.

* valid relationship types
* no self-links for prohibited relationship types

# 110. Performance Considerations

Knowledge Graph Expansion can dramatically increase graph size.

Therefore:

* use bounded traversals
* use indexes
* paginate
* cache common queries
* avoid default multi-layer traversal
* return compact nodes
* support incremental expansion

All of these are inherited from Phase 7.

---

# 111. Frontend Rendering Constraints

The backend should not assume the frontend can render unlimited nodes.

Recommended initial graph response:

```text
200 nodes
500 edges
```

Maximum should be configurable.


Example:

# 118. Definition of Done

Phase 8 is complete when LexGraph has evolved from:

```text
Word
 ↓
Ancestor
 ↓
Ancestor
```

into a **structured linguistic knowledge graph**:

```text
                           Indo-European
                                 │
                              Germanic
                                 │
                            West Germanic
                                 │
                              English
                                 │
                              father
                         ┌───────┼────────┐
                         │       │        │
                         ▼       ▼        ▼
                       fæder   fatherhood  parent
                         │
                         ▼
                      *fadēr
                         │
                         ▼
                      *ph₂tḗr
                     /    │     \
                    /     │      \
               Vater    vader    fader
                German   Dutch   Swedish
```

while maintaining a crucial distinction:

```text
                    ┌── Etymological ──┐
                    │                  │
                 ancestry          borrowing
                    │                  │
                    └──────┬───────────┘
                           │
                    Linguistic Graph
                           │
              ┌────────────┼────────────┐
              │            │            │
          Morphology     Language     Semantics
              │            │            │
          derivatives     families     meanings
```

The **most important success criterion** is not the number of entities or edges added.

It is that LexGraph can tell the user **what kind of relationship they are looking at and why that relationship exists**.

That distinction is what prevents the product from becoming merely a visually impressive network of words and turns it into a credible linguistic knowledge graph.
