Yes. Given the current state of LexGraph, I would treat these as **three implementation phases**:

1. **P0 — Data Quality, Provenance & Trust**
2. **P1 — Search Quality & Retrieval Evaluation**
3. **P1 — Production Security & Privacy**

The specifications below are deliberately implementation-oriented: they should be usable as development specifications for an agent or developer, not just as architectural recommendations.

# LexGraph — P0/P1 Technical Specifications

## Phase P0 — Data Quality, Provenance & Trust

### 1. Objective

Establish a trustworthy linguistic knowledge layer where every important lexical and etymological assertion can be:

* traced to its source;
* distinguished from generated/inferred data;
* assigned a confidence level;
* validated;
* detected when contradictory;
* reproduced from an ingestion run;
* audited when data changes.

The objective is **not merely importing more data**.

The objective is:

> **Every relationship displayed by LexGraph should have an explainable provenance trail.**

---

# 2. Problem Statement

Currently, a graph can conceptually look like:

```text
father
   │
   ▼
fæder
   │
   ▼
*fadēr
   │
   ▼
*ph₂tḗr
```

But the application ultimately needs to answer:

```text
Why does LexGraph believe these nodes are connected?

Which source says this?

Is this reconstructed?

Is it disputed?

Were multiple sources consulted?

When was the data imported?

Which version of the source produced this record?
```

Without this, the graph risks presenting uncertain linguistic hypotheses as established facts.

---

# 3. Core Principle

Separate:

### Entity

```text
father
```

from:

### Claim

```text
English "father" derives from Proto-Germanic "*fadēr".
```

from:

### Evidence

```text
Source X, version Y, page/entry Z.
```

This distinction should be reflected in the data model.

---

# 4. Target Data Model

Conceptually:

```text
Entity
  │
  └── Claim
        │
        ├── Relationship
        ├── Source
        ├── Evidence
        ├── Confidence
        └── IngestionRun
```

Example:

```text
Word: father

Claim:
  relationship = DERIVED_FROM
  target = Proto-Germanic *fadēr
  confidence = HIGH

Evidence:
  source = Wiktionary
  sourceVersion = ...
  sourceEntry = ...
  importedAt = ...
```

---

# 5. Provenance Model

Every imported assertion should carry at least:

```text
sourceId
sourceVersion
sourceRecordId
sourceUrl
sourceLicense
importRunId
importedAt
```

Where available:

```text
sourceEntry
sourcePage
sourceRevision
sourceLanguage
```

---

# 6. Source Entity

Create/extend:

```text
Source
```

with fields conceptually equivalent to:

```text
id
name
provider
version
url
license
licenseUrl
attributionRequired
commercialUseAllowed
redistributionAllowed
createdAt
updatedAt
```

Do not assume that because a source is publicly accessible it is automatically commercially redistributable.

---

# 7. Source Versioning

Sources must be versioned.

Example:

```text
Wiktionary
 ├── 2026-01
 ├── 2026-04
 └── 2026-08
```

An import must always identify which version was used.

Avoid:

```text
source = Wiktionary
```

without a version.

---

# 8. Import Run

Every ingestion operation must generate an `ImportRun`.

Example:

```text
ImportRun
---------
id
sourceId
sourceVersion
startedAt
completedAt
status
recordsRead
recordsCreated
recordsUpdated
recordsRejected
recordsSkipped
errors
checksum
```

Statuses:

```text
RUNNING
COMPLETED
FAILED
PARTIAL
ROLLED_BACK
```

---

# 9. Dataset Checksums

Store a checksum for imported datasets where practical.

Example:

```text
SHA-256
```

This allows you to establish:

> This database state came from exactly this source artifact.

---

# 10. Raw Data Preservation

Do not immediately discard the original source representation.

Preferred pipeline:

```text
Raw source
    ↓
Raw storage
    ↓
Parser
    ↓
Normalized representation
    ↓
Validation
    ↓
Canonical entities
    ↓
Claims
    ↓
Graph
```

The raw layer is valuable for debugging importer errors.

---

# 11. Canonical Entity Resolution

Multiple sources may describe the same entity.

For example:

```text
English
en
eng
English language
```

must resolve to one canonical language.

Create explicit normalization/resolution logic.

Do **not** rely only on string equality.

---

# 12. Entity Resolution

Potential matching signals:

### Language

* ISO 639 codes
* Glottocode
* canonical name
* aliases

### Word

* normalized form
* language
* script
* historical period
* lexical sense

### Source-specific identifier

Prefer stable source identifiers where available.

---

# 13. Word Identity

A word should not necessarily be identified only by:

```text
word.text
```

because:

```text
bank
```

can represent multiple senses and potentially different etymological histories.

A stronger conceptual identity is:

```text
WordForm
+
Language
+
Sense
+
Historical context
```

Do not over-normalize homonyms into one semantic entity.

---

# 14. Claim Model

Introduce a first-class claim concept.

Example:

```text
Claim
-----
subjectId
predicate
objectId
confidence
status
sourceId
evidenceId
createdAt
updatedAt
```

Example:

```text
father
DERIVED_FROM
*fadēr
```

---

# 15. Claim Status

Support:

```text
SUPPORTED
PROBABLE
POSSIBLE
DISPUTED
REJECTED
UNKNOWN
```

Do not reduce every linguistic claim to a binary true/false.

---

# 16. Confidence

Confidence should be distinct from status.

Example:

```text
status = SUPPORTED
confidence = 0.95
```

versus:

```text
status = POSSIBLE
confidence = 0.45
```

The numerical score should **not** pretend to represent mathematical probability unless it actually does.

Prefer terminology such as:

```text
confidenceScore
```

rather than:

```text
probability
```

---

# 17. Confidence Calculation

Initially, do not build a complicated ML confidence model.

Start with deterministic rules.

Example:

```text
+ strong authoritative source
+ multiple independent sources
+ consistent relationship
+ canonical language mapping
--------------------------------
higher confidence
```

Conversely:

```text
single source
+ explicitly uncertain source
+ conflicting evidence
--------------------------------
lower confidence
```

---

# 18. Source Agreement

If multiple sources independently support:

```text
A → B
```

represent that explicitly.

Example:

```text
Claim
 ├── Source A
 ├── Source B
 └── Source C
```

This is much better than overwriting one source with another.

---

# 19. Conflicting Claims

Suppose:

```text
Source A:
father → Proto-Germanic X

Source B:
father → Proto-Germanic Y
```

Do **not** silently choose one.

Represent:

```text
father
 ├──→ X   [Source A]
 └──→ Y   [Source B]
```

and mark the conflict.

---

# 20. Conflict Detection

Create a validation process capable of detecting:

```text
same subject
same relationship type
different object
```

where that combination should normally be unique.

These should become:

```text
CONFLICT
```

records or validation warnings.

---

# 21. Orphan Detection

Detect:

```text
Word with no language
Relationship with missing source
Relationship pointing to nonexistent entity
Language with no family
Meaning with no word
Source claim with missing provenance
```

Generate an import-quality report.

---

# 22. Graph Integrity Checks

Every graph edge should satisfy:

```text
source node exists
target node exists
relationship type exists
provenance exists
```

No dangling edges.

---

# 23. Language Integrity

Validate:

```text
language
   ↓
family
```

and historical relationships where applicable.

Detect:

```text
word.languageId → nonexistent language
```

before graph insertion.

---

# 24. Source Integrity

Every displayed etymological claim should be traceable to:

```text
Claim
 ↓
Evidence
 ↓
Source
 ↓
Source version
 ↓
Import run
```

This becomes a fundamental invariant.

---

# 25. Data Quality Dashboard

Create an internal admin/data-quality view.

Example:

```text
LexGraph Data Quality

Entities
────────────

Languages              7,812
Relationships       4,832,912

Quality
────────────
Orphan entities          132
Missing sources           41
Conflicting claims        83
Unresolved languages     219
Invalid relationships      7
```

---

# 26. Import Report

Every import should produce:

```text
Import completed

Source: Wiktionary
Version: 2026-08

Read:       4,231,221
Created:    1,231,220
Updated:      312,421
Rejected:       2,812
Duplicates:    82,311

```

---

# 27. Import Failure Policy

Never partially modify production data without knowing what happened.

Preferred:

```text
Import
 ↓
Validate
 ↓
Stage
 ↓
Quality checks
 ↓
Promote
```

rather than:

```text
Import directly into production
```

---

# 28. Staging Database/Tables

For major imports:

```text
staging_words
staging_relationships
staging_languages
```

Then validate before promotion.

This is especially important when ingesting millions of records.

---

# 29. Idempotent Imports

Running the same import twice must not create duplicates.

Example:

```text
import X
import X again
```

should produce approximately:

```text
0 new duplicate entities
```

Use stable source identifiers and unique constraints.

---

# 30. Data Versioning

The system should be able to answer:

> Which data version generated this graph?

Store:

```text
graphDataVersion
```

or equivalent metadata.

This becomes useful when a user saves a graph and the underlying dataset changes.

---

# 31. User-Facing Provenance

Don't expose the internal import architecture.

The UI should say:

```text
Source

Wiktionary
Revision: ...
Imported August 2026

Confidence: High
```

Then:

```text
View source
```

---

# 32. Graph Edge Provenance

Clicking an edge should show:

```text
DERIVED_FROM

Confidence: High

Sources:
• Source A
• Source B

Evidence:
...
```

This directly supports the product's core promise.

---

# 33. Data Quality Acceptance Criteria

Phase P0 is complete when:

* [ ] Every graph edge has provenance.
* [ ] Sources are versioned.
* [ ] Import runs are tracked.
* [ ] Imports are idempotent.
* [ ] Orphan detection exists.
* [ ] Duplicate detection exists.
* [ ] Conflict detection exists.
* [ ] Source licensing metadata exists.
* [ ] Import reports exist.
* [ ] Production imports use staging/validation.
* [ ] Users can inspect provenance.
* [ ] Data-quality metrics are measurable.
* [ ] No graph edge can exist without valid endpoints.
* [ ] No major source can be ingested without attribution/license metadata.

# Phase P1 — Search Quality & Retrieval Evaluation

## 1. Objective

Make LexGraph search **linguistically useful**, not merely technically functional.

The system should return the right lexical entity even when the user's input contains:

* accents
* case differences
* spelling variations
* historical forms
* transliteration
* alternate scripts
* partial words
* typos
* language ambiguity

---

# 2. Search Pipeline

Implement the search pipeline explicitly:

```text
User input
   ↓
Input normalization
   ↓
Exact match
   ↓
Canonical match
   ↓
Alias match
   ↓
Prefix match
   ↓
Fuzzy match
   ↓
Language/context filtering
   ↓
Ranking
   ↓
Result diversification
   ↓
SearchCandidate[]
```

---

# 3. Search Types

Classify matches.

```text
EXACT
CANONICAL
ALIAS
PREFIX
FUZZY
TRANSLITERATION
```

This information can be useful internally and potentially displayed subtly in the UI.

---

# 4. Normalization

Normalize:

* Unicode
* case
* whitespace
* punctuation where appropriate
* diacritics for fallback matching

Example:

```text
père
PÈRE
pere
```

should be related during search.

But:

> **Do not destroy the original form.**

Store/display:

```text
original = père
normalized = pere
```

---

# 5. Exact Match Priority

If the user searches:

```text
father
```

an exact English `father` should generally outrank:

```text
fathers
fatherhood
grandfather
```

---

# 6. Accent Handling

If the user searches:

```text
pere
```

the system should be able to find:

```text
père
```

but `père` should still retain its canonical spelling.

---

# 7. Fuzzy Search

Use PostgreSQL capabilities already present in your stack:

```text
pg_trgm
```

and potentially full-text search where appropriate.

Do not immediately introduce Elasticsearch/OpenSearch.

Benchmark PostgreSQL first.

---

# 8. Fuzzy Threshold

Do not use one arbitrary fuzzy threshold globally.

Different word lengths require different thresholds.

For example:

```text
short word
→ high precision requirement

long word
→ more tolerance
```

Define thresholds empirically through the benchmark dataset.

---

# 9. Ranking Model

A candidate score should combine multiple signals.

Conceptually:

```text
score =
    exactMatchWeight
  + normalizedMatchWeight
  + aliasWeight
  + prefixWeight
  + fuzzySimilarityWeight
  + languageMatchWeight
  + popularityWeight
  + lexicalConfidenceWeight
```

Keep the scoring implementation modular.

---

# 10. Language Context

If the user specifies:

```text
father — English
```

English should receive a major ranking boost.

Without a language filter:

```text
father
```

should potentially return multiple relevant lexical entities.

---

# 11. Search Result Model

Return structured information:

```text
SearchCandidate
{
    id
    text
    language
    normalizedText
    matchType
    score
    meaningPreview
}
```

Do not expose internal database details.

---

# 12. Search Result Ranking

The first result should generally be the most likely interpretation.

For:

```text
father
```

something like:

```text
father
English
noun — male parent

father
English
verb

father
German...
```

rather than an arbitrary database ordering.

---

# 13. Ambiguity Handling

If a word has multiple plausible interpretations:

```text
bank
```

do not pretend the system knows which one the user means.

Show:

```text
English
bank — financial institution

English
bank — side of a river
```

---

# 14. Search Suggestions

As the user types:

```text
fath
```

show suggestions.

But avoid querying the backend on every keystroke without control.

Use:

```text
debounce ~150–300ms
```

and cancellation.

---

# 15. Search Minimum Query Length

For fuzzy search:

```text
minimum 2–3 characters
```

depending on language.

Single-character fuzzy searches are generally not useful.

---

# 16. Query Cancellation

If the user types:

```text
f
fa
fat
fath
father
```

older requests should be cancelled or ignored.

Only the latest query should update the UI.

---

# 17. Search Cache

Cache popular searches.

Potential key:

```text
search:{normalizedQuery}:{language}:{filters}:{version}
```

Include relevant dataset version in the cache key.

---

# 18. Cache Invalidation

When the linguistic dataset changes:

```text
dataset version changes
        ↓
old search cache becomes invalid
```

Prefer versioned cache namespaces instead of trying to invalidate millions of individual keys.

---

# 19. Search Evaluation Dataset

This is the most important new artifact.

Create:

```text
tests/search/benchmark.json
```

or equivalent.

Each case:

```json
{
  "query": "father",
  "expected": [
    "canonical-word-id"
  ]
}
```

Support:

```text
expectedTop1
expectedTop5
acceptableResults
```

---

# 20. Benchmark Categories

Create test groups:

### Exact

```text
father
```

### Case

```text
Father
FATHER
```

### Accent

```text
pere
père
```

### Typo

```text
fathr
```

### Historical

```text
fæder
```

### Transliteration

```text
patēr
```

### Ambiguous

```text
bank
```

### Multilingual

```text
pai
father
pere
père
```

---

# 21. Metrics

Measure:

### Precision@1

How often the first result is correct.

### Precision@5

How often the correct result appears in top 5.

### Recall@10

Whether relevant candidates appear in top 10.

### MRR

Mean Reciprocal Rank.

This is particularly useful for ranking quality.

---

# 22. Target Metrics

Initial targets:

```text
Exact queries:
P@1 ≥ 99%

Normalized:
P@1 ≥ 98%

Common typo:
P@1 ≥ 90%

Ambiguous:
P@5 ≥ 95%

Historical/alternate:
P@5 ≥ 90%
```

These are starting targets, not universal truths. Measure them against real data.

---

# 23. Search Regression Testing

Every search ranking change should run the benchmark.

Example:

```text
Before:
MRR = 0.91

After:
MRR = 0.94
```

But also detect regressions:

```text
English: +4%
Latin: -12%
Historical forms: -18%
```

Do not optimize aggregate metrics while damaging specific language categories.

---

# 24. Search Quality by Language

Track metrics by:

```text
language
language family
script
word length
match type
```

You may discover:

```text
Latin → excellent
English → excellent
Greek → good
Arabic → poor
historical forms → poor
```

That tells you where the actual engineering work is.

---

# 25. Search Observability

Log/search metrics without unnecessarily storing personal queries.

Metrics:

```text
search_count
zero_result_count
latency
result_count
match_type
ranking_version
```

Potentially hash or aggregate queries for analytics where appropriate.

---

# 26. Zero-Result Analysis

Zero results are extremely valuable.

Track:

```text
query
normalized query
language context
```

subject to privacy policy.

Then categorize:

```text
unknown word
missing data
normalization problem
language-resolution problem
search bug
```

---

# 27. Search Feedback

Eventually add:

```text
Was this result useful?

👍
👎
```

This creates real training/evaluation data.

Don't make it mandatory.

---

# 28. Search Explainability

For debugging, be able to explain:

```text
Why did this result rank #1?
```

Example internal result:

```text
Exact match:       +100
Language match:     +40
Canonical form:     +20
Popularity:         +5
Total:             165
```

This will make tuning much easier.

---

# 29. Search Versioning

Give the ranking algorithm a version:

```text
rankingVersion = 3
```

This helps compare:

```text
v2 → v3
```

and invalidate caches safely.

---

# 30. Search Acceptance Criteria

Phase P1 Search is complete when:

* [ ] Exact searches are highly reliable.
* [ ] Accent normalization works.
* [ ] Case normalization works.
* [ ] Fuzzy search works.
* [ ] Historical forms are searchable.
* [ ] Ambiguous results are clearly presented.
* [ ] Search results are ranked deterministically.
* [ ] Search benchmark exists.
* [ ] P@1/P@5/Recall/MRR are measured.
* [ ] Regression testing is automated.
* [ ] Search latency is measured.
* [ ] Zero-result searches are measurable.
* [ ] Search cache is version-aware.
* [ ] Search behavior is evaluated by language.

# Phase P1 — Production Security & Privacy

## 1. Objective

Move LexGraph from:

> "security-conscious development"

to:

> **"safe enough to expose to real users and their private workspace data."**

The most important concern is now the boundary between:

```text
Public LexGraph
```

and:

```text
Private User Workspace
```

---

# 2. Security Model

Use explicit security boundaries:

```text
                    Request
                       │
                       ▼
                 Authentication
                       │
                       ▼
                 Authorization
                       │
             ┌─────────┴─────────┐
             │                   │
          Public              Private
             │                   │
       LexGraph data        User data
```

---

# 3. Authentication

Verify:

* password hashing
* session generation
* session expiry
* logout
* password reset
* email verification if enabled
* account recovery
* brute-force protection

Never implement cryptography yourself.

Use established libraries.

---

# 4. Password Storage

If passwords are handled directly:

Use a modern password hashing algorithm such as:

```text
Argon2id
```

Never:

```text
MD5
SHA1
SHA256(password)
```

without a password-specific KDF.

---

# 5. Session Security

Sessions must:

* expire
* be revocable
* use secure cookies where applicable
* use HttpOnly where applicable
* use appropriate SameSite policy
* rotate after sensitive events where appropriate

---

# 6. Authorization

Every private resource must verify ownership.

For example:

```text
GET /v1/me/notes/:id
```

must verify:

```text
note.userId === authenticatedUser.id
```

Server-side.

---

# 7. IDOR Testing

Explicitly test:

```text
User A
  ↓
/notes/USER_B_NOTE_ID
```

Expected:

```text
404 or 403
```

Never:

```text
200 + User B's note
```

Do the same for:

* collections
* saved words
* saved graphs
* preferences
* exports

---

# 8. `/me` Boundary

Prefer:

```text
/v1/me/*
```

for user-owned resources.

Avoid exposing:

```text
/v1/users/{userId}/notes
```

unless there is a concrete reason.

---

# 9. Mass Assignment Protection

Never allow the frontend to arbitrarily update:

```text
userId
role
permissions
createdAt
```

For example:

```json
{
  "name": "x",
  "userId": "someone-else"
}
```

must not be accepted.

Use explicit DTOs.

---

# 10. Role System

Keep roles minimal.

Initially:

```text
USER
ADMIN
```

Do not create:

```text
SUPER_ADMIN
EDITOR
MODERATOR
DATA_MANAGER
...
```

until actually needed.

---

# 11. Admin Separation

Administrative APIs must be clearly separated:

```text
/v1/admin/*
```

and require explicit admin authorization.

---

# 12. Rate Limiting

Rate-limit:

### Authentication

```text
login
register
password reset
```

### Search

Prevent abusive automated search.

### Graph traversal

Graph queries can be computationally expensive.

### Imports

Very strict.

### Exports

Very strict.

---

# 13. Graph Abuse Protection

A malicious request could ask:

```text
depth = 1000
```

and potentially explode the traversal.

Enforce:

```text
maxDepth
maxNodes
maxEdges
maxExecutionTime
```

Example starting limits:

```text
depth ≤ 10
nodes ≤ 5,000
edges ≤ 20,000
```

Adjust based on benchmarks.

---

# 14. Query Complexity

Never allow arbitrary graph queries directly from the public API.

Expose controlled operations:

```text
ancestors
descendants
neighborhood
lineage
```

rather than:

```text
execute arbitrary Cypher
```

---

# 15. Request Validation

Validate all external inputs:

```text
query
wordId
languageId
depth
limit
cursor
collectionId
note
```

Use schema validation consistently.

---

# 16. Numeric Limits

Every numeric parameter needs bounds.

Example:

```text
limit: 1–100
depth: 0–10
offset: 0–100000
```

Never allow:

```text
limit = 999999999
```

---

# 17. Payload Limits

Restrict:

```text
JSON body
note length
collection description
import size
export requests
```

This prevents memory abuse.

---

# 18. SQL Injection

Prisma helps considerably here.

Still:

> Any raw SQL or AGE/Cypher query construction must be treated as security-sensitive.

Never concatenate user input directly into queries.

Bad:

```text
"... WHERE name = '" + input + "'"
```

Use parameterized queries.

---

# 19. Cypher Injection

This deserves special attention because Apache AGE introduces another query language.

Do not interpolate:

```text
user input
```

into Cypher strings.

Parameterize or strictly validate all dynamic graph parameters.

---

# 20. XSS

User-generated content includes:

```text
notes
collection names
descriptions
profile data
```

Treat them as untrusted.

If Markdown is supported:

```text
Markdown
 ↓
sanitize
 ↓
HTML
```

Never render arbitrary HTML directly.

---

# 21. Stored XSS Test

Create a test payload such as:

```html
<script>alert(1)</script>
```

and verify it renders harmlessly.

Also test:

```html
<img src=x onerror=alert(1)>
```

and Markdown link/javascript variants.

---

# 22. CSRF

If authentication uses cookies, explicitly assess CSRF risk for state-changing operations:

```text
POST
PUT
PATCH
DELETE
```

Use appropriate CSRF protection and/or cookie/origin controls.

---

# 23. CORS

Do not configure:

```text
Access-Control-Allow-Origin: *
```

for authenticated APIs.

Explicitly allow the production frontend origin.

---

# 24. Security Headers

Production web application should use appropriate headers such as:

```text
Content-Security-Policy
Strict-Transport-Security
X-Content-Type-Options
Referrer-Policy
Permissions-Policy
```

Avoid blindly copying a CSP that breaks legitimate Next.js functionality; test it.

---

# 25. Secrets

Never commit:

```text
DATABASE_URL
JWT_SECRET
API_KEY
REDIS_PASSWORD
OAuth secret
```

Use environment variables/secrets management.

---

# 26. Environment Separation

Maintain:

```text
development
test
staging
production
```

with separate credentials and preferably separate databases.

Never run tests against production.

---

# 27. Database Permissions

The production application user should have only the privileges required.

Avoid using:

```text
postgres superuser
```

as the application runtime identity.

---

# 28. Database Network Security

Production PostgreSQL should not be publicly exposed unnecessarily.

Preferred:

```text
Internet
   ↓
API
   ↓
private DB connection
```

rather than:

```text
Internet
   ↓
PostgreSQL:5432
```

---

# 29. Redis Security

If Redis is used:

* require authentication where supported
* restrict network access
* never expose Redis publicly
* don't store sensitive data unnecessarily
* use TTLs

---

# 30. Cache Isolation

This is a critical issue.

Never allow:

```text
cache key:
workspace:notes
```

Instead:

```text
workspace:USER_ID:notes
```

or equivalent.

Otherwise:

```text
User A
 ↓
cache
 ↓
User B
```

could receive private data.

---

# 31. Cache Poisoning

Validate cacheable responses.

Do not allow arbitrary user-controlled data to determine security-sensitive cache keys or response behavior.

---

# 32. Authentication Enumeration

Avoid revealing:

```text
"email exists"
```

where that enables account enumeration.

Use generic responses where appropriate.

---

# 33. Logging

Never log:

```text
passwords
tokens
session cookies
authorization headers
private note contents
```

Potentially sensitive IDs should also be treated carefully.

---

# 34. Error Responses

Production API should not expose:

```text
stack traces
SQL errors
Cypher queries
filesystem paths
environment variables
```

Return structured errors:

```json
{
  "code": "RESOURCE_NOT_FOUND",
  "message": "The requested resource was not found."
}
```

---

# 35. Dependency Security

Automate:

```text
npm audit / equivalent
pip dependency audit
Dependabot/Renovate
GitHub security scanning
```

at least at a basic level.

---

# 36. Container Security

Production Docker images should:

* use minimal base images
* avoid unnecessary packages
* run as non-root where possible
* pin important versions
* scan for vulnerabilities

---

# 37. Docker Secrets

Do not bake secrets into:

```text
Dockerfile
image layers
docker-compose.yml committed to Git
```

---

# 38. Authentication Audit Events

Record security-relevant events:

```text
login success
login failure
logout
password reset
email change
account deletion
```

Do not log credentials.

---

# 39. Suspicious Activity

Eventually detect:

```text
1000 failed logins
10000 graph requests
mass export
```

and trigger rate limits or alerts.

---

# 40. Account Deletion

Deleting a user must remove/anonymize their private data.

But never delete shared LexGraph knowledge simply because a user account disappears.

---

# 41. Data Export

Export must require authentication.

It must never be publicly accessible through a predictable URL.

If generated asynchronously:

```text
export job
 ↓
private storage
 ↓
short-lived access
```

---

# 42. Import Security

Imports are an attack surface.

Validate:

```text
file size
JSON depth
record count
string length
schema
references
```

before processing.

---

# 43. Zip Bomb / Archive Protection

If archives are accepted:

```text
compressed size
uncompressed size
file count
nesting depth
```

must be limited.

If you don't need archives, don't support them initially.

---

# 44. SSRF

If LexGraph allows users/admins to provide URLs for source ingestion, validate them carefully.

Never allow arbitrary internal URLs such as:

```text
localhost
127.0.0.1
169.254.x.x
private network ranges
```

unless explicitly required.

---

# 45. Source Ingestion Security

The import system should be isolated from the public web application.

Preferred:

```text
Web
 ↓
Import job
 ↓
Worker
 ↓
Staging
 ↓
Validation
 ↓
Production DB
```

rather than allowing arbitrary users to trigger arbitrary import commands.

---

Create automated tests for:

| Area          | Test                   |
| ------------- | ---------------------- |
| Auth          | Invalid credentials    |
| Auth          | Brute force            |
| Session       | Expiration             |
| Session       | Revocation             |
| Authorization | User A → User B        |
| Notes         | IDOR                   |
| Collections   | IDOR                   |
| Graphs        | IDOR                   |
| Search        | Abuse                  |
| Graph         | Excessive depth        |
| Graph         | Excessive nodes        |
| SQL           | Injection              |
| AGE           | Cypher injection       |
| XSS           | Stored payload         |
| CSRF          | State-changing request |
| CORS          | Unauthorized origin    |

# 47. Production Security Acceptance Criteria

Phase P1 Security is complete when:

* [ ] All private endpoints enforce authentication.
* [ ] All private resources enforce authorization.
* [ ] IDOR tests pass.
* [ ] Passwords use secure password hashing if locally managed.
* [ ] Sessions expire and can be revoked.
* [ ] Authentication endpoints are rate-limited.
* [ ] Graph traversal has hard limits.
* [ ] SQL injection tests pass.
* [ ] Cypher injection tests pass.
* [ ] Stored XSS tests pass.
* [ ] CSRF protection is validated.
* [ ] CORS is restricted.
* [ ] Security headers are configured.
* [ ] Secrets are externalized.
* [ ] Production DB isn't publicly exposed unnecessarily.
* [ ] Redis isn't publicly exposed.
* [ ] Private cache entries are user-isolated.
* [ ] Sensitive information is absent from logs.
* [ ] Production errors don't expose internals.
* [ ] Dependency scanning is automated.
* [ ] Container vulnerabilities are monitored.
* [ ] Import/export security is tested.
* [ ] Account deletion works correctly.
* [ ] Security events are observable.

# Recommended execution order

I would **not execute these three phases sequentially in the exact order above**. There are dependencies.

Use this sequence:

          │                   │
          ▼                   ▼
      P1 SEARCH          P1 SECURITY

## The three phases have different success criteria

This distinction matters.

### P0 asks:

> **"Can I trust the information?"**

### P1 Search asks:

> **"Can I reliably find the information I want?"**

### P1 Security asks:

> **"Can I safely expose this system to real users?"**

Only when all three are reasonably strong does LexGraph become ready for the next major step:

```text
                    LEXGRAPH
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   TRUSTWORTHY      FINDABLE        SECURE
      DATA          SEARCH           USERS
        │              │              │
        └──────────────┼──────────────┘
                       ▼
                Excellent UX
                       │
                       ▼
                Public Product
```

**My priority remains P0 > Search > Security**, but security should be treated as a **release gate**: you can improve search continuously, but you should not expose the authenticated workspace publicly until the critical security acceptance criteria pass.
