# Phase 5 — Search & Discovery Engine Specification

## 1. Overview

### Goal

Transform LexGraph search from a basic word lookup into a **fast, multilingual discovery engine** that allows users to find words, languages, roots, meanings, and relationships and immediately continue exploring the knowledge graph.

The search experience must work naturally with the Graph Workspace established in Phases 1–4.

The core principle is:

> **Search should be the beginning of exploration, not the end of a query.**

---

# 2. Product Objectives

By the end of Phase 5, users should be able to:

* Search for words in any supported language.
* Search using partial words.
* Search with spelling mistakes.
* Search using normalized/unaccented forms.
* Search by meaning.
* Search for historical forms.
* Search for reconstructed roots.
* Search for languages and language families.
* Understand why a result matched.
* Quickly identify the correct result among similar words.
* Open a result directly in the Graph Workspace.
* Continue searching without leaving the workspace.
* Search the currently visible graph.
* Navigate the entire search experience using the keyboard.

---

# 3. Search Architecture

The architecture should separate **search infrastructure** from **search presentation**.

```text
                     User
                      │
                      ▼
              Search Interface
                      │
                      ▼
              Search Application
                      │
             ┌────────┴────────┐
             ▼                 ▼
       Global Search      Graph Search
             │                 │
             ▼                 ▼
       Search Service    Graph State
             │
             ▼
       Search Index
             │
             ▼
    Canonical LexGraph DB
```

The frontend must never query the database directly.

```text
Web App
   │
   ▼
LexGraph API
   │
   ▼
Search Application Service
   │
   ▼
Search Infrastructure
   │
   ▼
Canonical Database / Search Index
```

# 5. Search Modes

The application should support three distinct search contexts.

## 5.1 Global Search

Searches the complete LexGraph dataset.

Example:

```text
father
```

Returns all relevant entities.

---

## 5.2 Workspace Search

Searches from within the Graph Workspace.

Example:

```text
father
```

The workspace changes its root graph.

No full-page navigation.

---

## 5.3 Graph Search

Searches only entities currently loaded in the graph.

Example:

```text
German
```

Results highlight matching nodes already present in the graph.

These modes must not be confused in the UI.

# 9. Input Normalization

Before searching, normalize the query.

Requirements:

* Unicode normalization
* trim whitespace
* collapse repeated whitespace
* case normalization
* optional accent-insensitive comparison
* punctuation normalization

Examples:

```text
FATHER
```

→

```text
father
```

---

```text
naïve
```

should optionally match:

```text
naive
```

without losing the original spelling.

---

# 10. Unicode Handling

This is particularly important for LexGraph.

The system must support:

* IPA
* diacritics
* combining characters
* reconstructed Proto-Languages
* special linguistic characters

Examples:

```text
*ph₂tḗr
fæder
þæt
Ƿ
ā
ē
ī
ō
ū
```

Never strip linguistic characters during normalization.

Normalization must create **search representations**, not overwrite canonical text.

---

# 11. Exact Match

Exact matches receive the highest ranking.

Query:

```text
father
```

Result:

```text
father — English
```

should outrank:

```text
fatherhood
```

and:

```text
godfather
```

---

# 12. Prefix Matching

Query:

```text
fat
```

Possible results:

```text
father
fate
fatal
fatigue
```

Prefix matches should rank above arbitrary substring matches.

---

# 13. Substring Matching

Query:

```text
ther
```

Possible result:

```text
father
mother
brother
```

Substring matches should have lower priority than exact/prefix matches.

---

# 14. Fuzzy Matching

Support reasonable spelling errors.

Example:

```text
fater
```

→

```text
father
```

Another:

```text
Vather
```

→

```text
Vater
```

Fuzzy matching must have a threshold to prevent irrelevant results.

---

# 15. Fuzzy Search Constraints

Do not perform expensive fuzzy matching against the entire database for every keystroke.

Use:

1. Exact/prefix index
2. Full-text index
3. Trigram/fuzzy index
4. Semantic search only where justified

This protects performance.

---

# 16. Meaning Search

Search should eventually allow:

```text
parent
```

to find:

```text
father
mother
ancestor
progenitor
```

The result should explain the match.

Example:

```text
father
English
Meaning match: "male parent"
```

This is important because otherwise users cannot distinguish an exact lexical match from a semantic match.

---

# 17. Multilingual Search

A user should not need to specify the language.

Query:

```text
pater
```

could return:

```text
pater — Latin
pater — Romanian
pater — historical forms
```

The UI must clearly distinguish them.

# 23. Search Ranking

Ranking should be deterministic and explainable.

Initial priority:

```text
Exact word
    ↓
Exact normalized word
    ↓
Prefix
    ↓
Historical exact
    ↓
Root exact
    ↓
Substring
    ↓
Meaning
    ↓
Fuzzy
```

Ranking can then incorporate additional signals:

* language relevance
* popularity
* source confidence
* data completeness
* historical importance

Do not introduce opaque ML ranking at this stage.

---

# 24. Ranking Example

Query:

```text
father
```

Expected ordering:

```text
1. father — English
2. father — historical English
3. fatherhood — English
4. godfather — English
5. pater — Latin
```

The exact ordering may evolve with the dataset, but relevance must remain explainable.

# 25. Autocomplete

Autocomplete should begin after a small minimum query length.

```text

```

This threshold can be adjusted based on measured performance.

The exact value should be measured rather than treated as a hard requirement.

# 36. Search Existing Workspace

If the user searches for:

```text
Vater
```

while exploring:

```text

```

the application should not necessarily discard the current graph immediately.

Preferred behavior:

```text

     ↓
Select Vater
     ↓

"Open as root"
"Add to graph"
```

The first implementation can default to replacing the root.

The architecture should support graph insertion later.

# 47. Request Cancellation

```text

```


Never allow an older response to overwrite newer results.

# 51. Search Index

The search layer should not rely exclusively on database scans.

Recommended PostgreSQL capabilities:

* B-tree indexes
* PostgreSQL full-text search
* `pg_trgm`
* GIN indexes
* normalized search columns

Potential future dedicated search engine:

* OpenSearch
* Elasticsearch
* Meilisearch
* Typesense

Do **not** introduce one unless PostgreSQL can no longer meet measured requirements.

---

# 70. Acceptance Criteria

Phase 5 is complete when:

### Search

* A user can search for words from anywhere in LexGraph.
* Exact matches are returned first.
* Prefix searches work.
* Reasonable misspellings are handled.
* Unicode and linguistic characters work correctly.
* Multiple languages are supported.
* Languages and language families can be searched.
* Meanings can be searched where supported.

### UX

* Autocomplete feels immediate.
* Keyboard navigation works.
* Search works on mobile.
* No-result states provide useful next actions.
* Search does not disrupt the workspace.
* Selecting a result opens the correct graph context.

### Technical

* Search uses proper indexes.
* Search requests are cancellable.
* Results are ranked deterministically.
* Search does not scan the entire database unnecessarily.
* Search performance is measured against representative datasets.
* Search behavior is covered by automated tests.

### Product

Most importantly:

> A user who arrives at LexGraph with a word in mind should be able to find it quickly and naturally transition from that word into discovering its linguistic history and relationships.

---

# 71. Out of Scope

Do not implement in Phase 5:

* AI-powered semantic search
* LLM-generated answers
* voice search
* image/OCR search
* personalized search ranking
* social search
* user-generated content search
* recommendation models
* dedicated Elasticsearch/OpenSearch infrastructure unless benchmarks prove PostgreSQL insufficient

These can be considered later.

---

# 72. Definition of Done

Phase 5 is complete when LexGraph has a **fast, multilingual, linguistically aware search and discovery engine** that connects the user's intent directly to the knowledge graph.

The user should be able to go from:

```text
"I wonder where the word father came from"
```

to:

```text
father
    ↓
Old English fæder
    ↓
Proto-Germanic
    ↓
Proto-Indo-European *ph₂tḗr
```

with minimal friction.

The search engine's job is therefore not simply to **find words**.

Its job is to **open the door to the graph**.
