# Phase 6 — Word Inspector & Knowledge Panels Specification

---

## 1. Overview

### Goal

Transform the selected word from a simple graph node into a **rich linguistic entity** that users can inspect, understand, verify, and use as the starting point for further exploration.

The Word Inspector is the primary information interface between the **graph** and the **underlying LexGraph knowledge model**.

The user should be able to select a node and immediately understand:

* What the word is.
* Which language it belongs to.
* What it means.
* Where it came from.
* What languages/forms it is related to.
* How confident LexGraph is about each relationship.
* Where the information came from.
* What they can explore next.

---

# 2. Product Principle

The inspector should answer three questions progressively:

### 1. What is this?

```text
father
English
noun
```

### 2. Where did it come from?

```text
father
   ↓
Old English fæder
   ↓
Proto-Germanic
   ↓
Proto-Indo-European *ph₂tḗr
```

### 3. What can I discover next?

```text
Cognates
Borrowings
Descendants
Related meanings
Language family
Historical forms
```

The inspector should therefore function as both:

* **information panel**
* **navigation hub**

---

# 3. Core UX Model

The inspector is contextual.

```text
Graph
  │
  │ click node
  ▼
Word Inspector
  │
  ├── Overview
  ├── Meaning
  ├── Pronunciation
  ├── Etymology
  ├── Relationships
  ├── Timeline
  ├── Sources
  └── Explore
```

The graph remains visible whenever screen size allows.

The inspector should not feel like navigating to a separate dictionary page.

# 6. Inspector States

The component must support:

### Closed

No entity selected.

### Loading

Entity selected but data loading.

### Loaded

Complete or partial entity available.

### Error

Data unavailable.

### Not Found

Entity no longer exists.

# 16. Historical Status

Historical forms should be visually obvious.


# 17. Etymology Section

This is a core differentiator of LexGraph.

Example:

```text
Etymology

English father

← Old English fæder

← Proto-Germanic *fadēr

← Proto-Indo-European *ph₂tḗr
```

Each item should be clickable.

Clicking:

```text
fæder
```

selects that node.

---

# 18. Etymology Visualization

The inspector may contain a compact lineage.

```text
father
  │
  ▼

  │

  ▼

```

This is not a replacement for the main graph.

# 20. Relationship Counts

For large graphs:

```text
Ancestors       4
Descendants    12
Cognates        9

```

Clicking a category expands it.

---

# 21. Relationship Semantics

Never display only:

```text
Related word
```

Use explicit relationships.

Examples:

```text
Inherited from
Borrowed from
Derived from
Cognate with
Variant of
Descendant of
```

This is critical to the credibility of LexGraph.

---

# 22. Relationship Evidence

Every important relationship should be inspectable.

Example:

```text

```

Selecting the relationship opens:


---

# 23. Confidence

Display confidence only when meaningful.

Example:

```text
Confidence
94%
```

Better:

```text
High confidence
```

with the numerical value available in details.

Avoid making users interpret arbitrary numbers everywhere.

---

# 24. Confidence Levels

Recommended:

```text
High
≥ 0.90

Medium
0.70–0.89

Low
< 0.70
```

The thresholds should be configurable.

---

# 25. Provenance

The inspector must make source information visible.

Example:

```text
Sources

Wiktionary
Glottolog
DBnary
```

Each source should show:

* dataset
* version
* reference
* attribution/license where appropriate

---

# 26. Source Details

Example:

```text
Wiktionary

Dataset version:
2026-08

Imported:
08 Aug 2026

Record:
...

License:
CC BY-SA
```

Users should not need to understand the import architecture to inspect provenance.

---

# 27. Conflicting Sources

If sources disagree, do not silently select one.

Example:

```text
Etymology

Two sources provide different intermediate forms.

Source A
Proto-Germanic *fadēr

Source B
Old Saxon fadar
```

Display:

```text
Multiple hypotheses
```

and allow comparison.

---

# 28. Data Completeness

The inspector should distinguish:

```text
Verified information
Missing information
Conflicting information
Inferred information
```

Example:

```text
⚠ Etymology uncertain
```

rather than presenting speculation as fact.

---

# 43. Focus Node

When the inspector opens:

```text
Selected node
    ↓
Inspector
```

Possible effects:

* highlight
* subtle glow
* connected-edge emphasis

Avoid excessive animation.

---

# 44. Inspector ↔ Graph Synchronization

The two components must share a common selection state.

```text
Graph Selection
      │
      ▼
Selected Entity
      │
 ┌────┴────┐
 ▼         ▼
Graph    Inspector
```

Clicking a graph node updates the inspector.

Clicking a relationship in the inspector updates the graph.

---

# 45. URL State

The selected entity should be representable in the URL.

Example:

```text
/words/{wordId}
```

or:

```text
/graph?root={wordId}&selected={wordId}
```

This enables:

* deep linking
* browser history
* sharing
* refresh persistence

---

# 46. Browser History

Inspector selection should not necessarily create a history entry for every click.

Recommended:

* opening a new root → history entry
* selecting an adjacent node → replace state or lightweight history
* explicit navigation → history entry

The exact behavior should be validated through UX testing.

---

# 47. Shareable Entity

Provide:

```text
Copy link
```

The copied URL should reopen:

* graph context
* selected word
* relevant inspector state

where practical.

---

# 48. Loading Experience

Use skeletons for:

```text
Word
Language
Meaning
Etymology
Relations
```

Do not show a blank panel.

---

# 49. Progressive Loading

The inspector should load high-value information first.

Recommended order:

```text
1. Word identity
2. Language
3. Meaning
4. Etymology
5. Relationships
6. Sources
7. Secondary metadata
```

The user should be able to start reading before everything has loaded.

---

# 50. Error Handling

If part of the data fails:

```text
Meaning
✓ Available

Etymology
⚠ Unable to load

Sources
✓ Available
```

Do not fail the entire inspector because one section failed.

---

# 51. Not Found

If the selected entity doesn't exist:

```text
Word not found

This entity may have been removed
or is no longer available.

Back to graph
```

---

# 52. Missing Data

Missing information should be represented honestly.

Example:

```text
Etymology

No etymological information is currently
available for this word.
```

Do not fabricate information.

---

# 53. Full Word Page

The inspector and full word page should use the same underlying components.

```text

     │
     ├── WordHeader
     ├── MeaningSection
     ├── EtymologySection
     ├── RelationshipSection
     ├── SourceSection
     └── ExploreSection
```

The full page composes the same components into a larger layout.

This avoids maintaining two implementations.


# 58. Information Density

The inspector should be dense enough for researchers but understandable to casual users.

Use progressive disclosure.

Example:

```text
Etymology
────────────

father
↓
fæder
↓
*fadēr

[View details]
```

rather than immediately showing every source, parser version, record ID, and confidence value.

---

# 59. Advanced Details

Expert users should be able to expand:

```text
Technical details
```

Containing:

* canonical ID
* source IDs
* dataset versions
* confidence
* import version
* timestamps
* relationship IDs

This keeps the normal interface clean.

# 60. Data Model

The frontend should consume a dedicated knowledge-panel response rather than assembling dozens of API calls.

Example:

```json
{
  "entity": {
    "id": "uuid",
    "type": "word",
    "text": "father",
    "language": {
      "id": "uuid",
      "name": "English",
      "family": "Germanic"
    }
  },
  "meanings": [],
  "pronunciations": [],
  "etymology": {},
  "relationships": [],
  "timeline": [],
  "sources": [],
  "metadata": {}
}
```

# 61. API

Recommended endpoint:

```http
GET /v1/words/{wordId}/inspector
```

Alternative:

```http
GET /v1/entities/{entityId}/knowledge-panel
```

The second option is more future-proof if the inspector eventually supports languages, roots, and other entities.

---

# 62. Recommendation

I recommend:

```http
GET /v1/entities/{entityId}/knowledge-panel
```

because LexGraph is evolving beyond a word dictionary.

Today:

```text
Word
```

Tomorrow:

```text
Language
Root
Family
Meaning
Evolution Event
```

The frontend should not need a different architectural pattern for every entity.

---

# 63. Relationship API

For expansion actions:

```http
GET /v1/entities/{entityId}/relationships?type=ancestor
```

Potential future:

```http
GET /v1/entities/{entityId}/relationships
```

with filtering and pagination.

---

# 64. Caching

Knowledge panels are excellent cache candidates.

Use TanStack Query.

Cache by:

```text
entityId
```

Potential stale time:

```text
5–30 minutes
```

Exact value should depend on how frequently the canonical dataset changes.

---

# 65. Backend Performance

The knowledge panel should avoid N+1 queries.

Bad:

```text
Word
 ↓
query language
 ↓
query family
 ↓
query meanings
 ↓
query relations
 ↓
query sources
```

Prefer:

```text
Single optimized knowledge-panel query
```

or a small number of parallel queries.

---

# 66. Database Optimization

Potential tools:

* indexes
* materialized views
* graph traversal optimization
* cached relationship summaries
* precomputed counts

Do not prematurely materialize everything.

Measure first.

```text
<300ms
```

for cached/common entities under normal production conditions.

Initial render should show identity information earlier if the full response takes longer.

# 71. Acceptance Criteria

Phase 6 is complete when:

### Information

A user selecting a word can clearly see:

* word
* language
* language family
* meaning
* part of speech
* pronunciation where available
* etymology where available
* historical forms
* relationships
* provenance
* confidence

### Graph Integration

* Selecting a graph node opens its inspector.
* Selecting another node updates the inspector.
* Clicking an entity inside the inspector updates the graph.
* Users can expand relevant relationships directly from the inspector.
* Inspector state can be represented in a shareable URL.

### Data Integrity

* Sources are clearly identified.
* Conflicting information is not silently discarded.
* Missing information is explicitly indicated.
* Reconstructed forms are distinguished from attested forms.
* Confidence is never presented as certainty.

### UX

* The graph remains the primary workspace.
* The inspector does not unnecessarily navigate away.
* Desktop and mobile layouts work correctly.
* Loading and errors are handled gracefully.
* Advanced metadata does not overwhelm normal users.

---

# 72. Out of Scope

Do not implement in this phase:

* AI-generated etymology
* AI-generated definitions
* User editing
* Community voting
* Automatic correction of source data
* Full linguistic analysis
* Audio generation
* Translation engine
* Personalized knowledge panels
* Social features

These should remain separate concerns.

---

# 73. Definition of Done

Phase 6 is complete when selecting any supported LexGraph entity produces a **trustworthy, readable, and interactive knowledge panel** that connects the entity's linguistic information directly to the graph.

The experience should move naturally from:

```text
                  father
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
       Meaning   Etymology  Language
          │         │         │
          ▼         ▼         ▼
       "male      fæder     English
       parent"      │          │
                    ▼          ▼
                Proto-      Germanic
                Germanic
```

to:

```text
Sources
Confidence
Historical context
Related words
Cognates
Ancestors
Descendants
```

without forcing the user to leave the graph.

**The strongest version of this phase is not "a better word details page." It is the creation of LexGraph's canonical information layer: the interface where graph entities, linguistic facts, provenance, and exploration all meet.**
