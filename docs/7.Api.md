# Phase 7 — Graph API & Backend Optimization Specification

## 1. Overview

### Goal

Transform LexGraph's backend from a functional graph API into a **production-ready graph platform** capable of supporting:

* fast graph exploration
* multi-level ancestry queries
* descendants and cognates
* interactive graph expansion
* large datasets
* concurrent users
* predictable API behavior
* efficient PostgreSQL/graph queries
* caching
* pagination
* observability
* future recommendation and discovery features

Phase 7 is primarily a **backend architecture and performance phase**.

The objective is not simply to make individual endpoints faster.

The objective is to establish a backend architecture that can scale as the LexGraph dataset grows from thousands to millions of linguistic entities and relationships.

---

# 3. Primary Objectives

Phase 7 must establish:

1. A clean graph API contract.
2. Efficient graph traversal.
3. Predictable query complexity.
4. Protection against expensive requests.
5. Efficient graph serialization.
6. Caching.
7. Pagination and limits.
8. Graph expansion endpoints.
9. Backend observability.
10. Performance benchmarks.
11. Database optimization.
12. Production-grade error handling.
13. API versioning.
14. Test coverage.
15. A clear path toward horizontal scaling.

---

# 4. Non-Goals

Do **not** attempt to solve everything in this phase.

Out of scope:

* AI-generated etymology
* AI semantic search
* community editing
* real-time collaboration
* distributed graph database migration
* Kubernetes deployment
* microservices decomposition
* machine-learning ranking
* automatic linguistic inference

The backend should remain relatively simple.

---

# 5. Core Architectural Principle

The API must expose **domain operations**, not database operations.

Bad:

```http
GET /graph/query?cypher=...
```

Good:

```http
GET /v1/graph/ancestors/{entityId}
```

The client should never know:

* PostgreSQL schema
* Cypher syntax
* SQL structure
* database implementation
* graph database vendor

This allows the backend to evolve independently.

# 17. Depth Limits

Never allow unlimited traversal.

Recommended default:

```text
depth = 3
```

Maximum:

```text
depth = 10
```

The maximum should be configurable.

---

# 18. Why Depth Limits Matter

Without limits:

```text
GET /graph/ancestors/id
```

could potentially traverse thousands or millions of relationships.

One malicious or accidental request could overwhelm the database.

---

# 19. Node Limits

Also limit the number of returned nodes.

Example:

```text
default: 200
maximum: 2,000
```

The exact values should be benchmarked.

---

# 20. Edge Limits

Edges should also be bounded.

Example:

```text
default: 500
maximum: 5,000
```

---

# 21. Traversal Cost Protection

The backend should estimate query complexity.

Example:

```text
depth × branching factor
```

If a query is potentially expensive:

```json
{
  "error": {
    "code": "GRAPH_QUERY_TOO_COMPLEX",
    "message": "The requested graph exceeds the allowed traversal size."
  }
}
```

---

# 22. Graph Expansion

Graph expansion is one of the most important API operations.

User:

```text
father
```

loads:

```text
father
 ├── fæder
 └── ...
```

User clicks:

```text
Expand ancestors
```

API should return only the new graph content.

Do not reload the entire graph unnecessarily.

---

# 23. Expansion API

Example:

```http
GET /v1/graph/{entityId}/expand?direction=ancestors&depth=1
```

Response:

```json
{
  "nodes": [],
  "edges": [],
  "meta": {
    "direction": "ancestors",
    "depth": 1
  }
}
```

Frontend merges these nodes into its current graph.

---

# 24. Why Incremental Expansion Matters

Bad:

```text
Every click
    ↓
reload entire graph
```

Good:

```text
Current graph
    +
new nodes
    +
new edges
```

This dramatically reduces:

* network traffic
* database work
* frontend rendering
* graph layout work

# 29. Graph Paths

Example:

```text

 ↓

 ↓

 ↓
*ph₂tḗr
```

API:

```http
GET /v1/graph/path?from=fatherId&to=rootId
```

Response:

```json
{
  "path": {
    "nodes": [],
    "edges": []
  }
}
```

---

# 30. Shortest Path

The backend should support shortest-path queries where appropriate.

Do not assume shortest path always equals linguistic history.

The API must describe the result as:

```text
Graph path
```

rather than:

```text
True etymology
```

unless the relationship semantics guarantee that interpretation.

---

# 31. Graph Semantics

Relationship types must be explicit.

Examples:

```text
INHERITED_FROM
BORROWED_FROM
DERIVED_FROM
COGNATE_WITH
VARIANT_OF
DESCENDANT_OF
RELATED_TO
```

Do not collapse everything into:

```text
RELATED
```

---

# 32. Directed Relationships

Relationships must retain direction.

Example:

```text
father
   │
   ▼
fæder
```

must not be treated as equivalent to:

```text
fæder
   │
   ▼
father
```

The UI may display the relationship in a user-friendly direction, but the backend must preserve canonical direction.

---

# 33. Graph Traversal Semantics

Define traversal rules per relationship.

Example:

```text
INHERITED_FROM
→ ancestors

DESCENDANT_OF
→ descendants

COGNATE_WITH
→ related/cognates
```

This should be configuration-driven rather than duplicated throughout the codebase.

---

# 34. Cycle Detection

The graph must handle cycles.

Example:

```text
A → B → C → A
```

Traversal must maintain a visited set.

Never allow infinite traversal.

---

# 35. Duplicate Nodes

When multiple paths reach the same entity:

```text
A → B
A → C → B
```

`B` should appear only once in the returned node set.

Both relationships may be returned.

---

# 36. Graph Serialization

Use compact JSON.

Avoid returning:

* database metadata
* internal query plans
* unnecessary source records
* duplicate entity information

---

# 37. Response Compression

Enable HTTP compression where appropriate.

Use:

```text
gzip
brotli
```

especially for large graph responses.

---

# 38. Pagination

Large relationship sets should support pagination.

Example:

```http
GET /v1/entities/{id}/relationships?limit=50&cursor=...
```

Prefer cursor pagination.

---

# 39. Cursor Design

Cursor should be opaque.

Example:

```text
cursor=eyJpZCI6IjEyMyJ9
```

Do not expose internal database offsets.

---

# 40. API Versioning

Current API:

```text
/v1/
```

Maintain backwards compatibility within v1.

Breaking changes require:

```text
/v2/
```

# 45. Database Optimization

The database is the most important performance component.

Optimization should start with measurement.

Do not optimize queries based on intuition alone.

---

# 46. Query Analysis

For every important graph query:

```sql
EXPLAIN ANALYZE
```

must be available during development.

Track:

* execution time
* rows scanned
* rows returned
* index usage
* joins
* memory
* sort operations

---

# 47. Required Indexes

Evaluate indexes for:

### Entities

```text
id
type
language_id
normalized_text
```

### Relationships

```text
source_id
target_id
relationship_type
(source_id, relationship_type)
(target_id, relationship_type)
```

---

# 48. Composite Indexes

Common traversal:

```text
WHERE source_id = ?
AND relationship_type = ?
```

should have a matching composite index where profiling demonstrates value.

---

# 49. Avoid N+1 Queries

Bad:

```text
Get 100 nodes

↓

100 language queries
```

Good:

```text
Get 100 nodes

↓

Single batched language query
```

---

# 50. Batch Loading

Use batching for:

* languages
* meanings
* sources
* relationship metadata
* provenance

---

# 51. Graph Query Optimization

Prefer bounded traversal.

Bad:

```text
MATCH path=(n)-[*]->(x)
```

Good:

```text
MATCH path=(n)-[*1..4]->(x)
```

---

# 52. Relationship Filtering at Database Level

Do not fetch everything and filter in application code.

Bad:

```text
Database
 ↓
all relationships
 ↓
backend filters
```

Good:

```text
Database
 ↓
only requested relationships
```

---

# 53. Projection

Only select fields needed for the API response.

Do not retrieve entire records if the endpoint needs:

```text
id
label
language
```

---

# 54. Materialized Views

Consider materialized views for expensive, stable information such as:

```text
word summary
language hierarchy
relationship counts
search documents
```

Do not materialize dynamic graph traversals unnecessarily.

---

# 55. Graph Summary Cache

Some graph metadata can be precomputed:

```text
ancestor count
descendant count
cognate count
relationship count
```

This allows the inspector to load summaries quickly.

---

# 56. Caching Architecture

Recommended:

```text
Frontend cache
      ↓
API cache
      ↓
Database
```

Initial backend cache can be:

```text
Redis
```

or an in-process cache for a single-instance deployment.

Do not introduce Redis solely because it is common.

Measure first.

---

# 57. Cache Candidates

Excellent cache candidates:

* word details
* language details
* knowledge panels
* common graph roots
* language family hierarchy

Poor candidates:

* arbitrary huge traversals
* highly personalized queries
* extremely filtered searches

---

# 58. Cache Keys

Example:

```text
graph:ancestors:{entityId}:depth:{depth}:v1
```

Search:

```text
search:{normalizedQuery}:{filters}:v1
```

Knowledge panel:

```text

```

---

# 59. Cache Invalidation

Because Phase 4 introduces dataset versions, cache invalidation should be version-aware.

Example:

```text
dataset:v42
```

Cache key:

```text
panel:v42:{entityId}
```

When dataset version changes, old cache entries naturally become obsolete.

This is preferable to attempting complex invalidation everywhere.

# 64. Request Validation

Validate:

* UUID format
* depth
* limits
* cursor
* entity type
* relationship type
* query length

Reject invalid requests before database execution.

---

# 65. Maximum Request Size

Prevent abuse through:

* enormous query parameters
* huge filter arrays
* extremely long strings

---

# 66. Timeout Policy

Every expensive database operation should have a bounded timeout.

Example:

```text
normal query: 1–2 seconds
complex graph query: configurable
```

Do not allow indefinite database execution.

---

# 67. Async Operations

Some operations may eventually become asynchronous.

Examples:

```text

Full lineage calculation
Dataset rebuild
Index rebuild
```

Do not force long-running work into normal HTTP requests.

# 77. Connection Pooling

Configure PostgreSQL connection pooling.

Avoid:

```text
one connection per request
```

Use a bounded pool.

Monitor:

```text
active
idle
waiting
```

---

# 78. Transaction Management

Keep transactions short.

Avoid holding transactions open while:

* serializing responses
* calling external services
* performing graph layout
* waiting for unrelated work

---

# 79. Read vs Write Separation

Most production LexGraph traffic will be read-heavy.

Architecture should allow future:

```text
Write DB
     ↓
Read Replica(s)
```

Do not implement replicas unless required.

But repositories should avoid assumptions that make replication impossible later.

---

# 80. Database Migrations

Use a formal migration system.

Every schema change must be:

* versioned
* reversible where practical
* tested
* documented

Never modify production schema manually.

---

# 81. API Contract

Maintain OpenAPI documentation.

Every endpoint should document:

* parameters
* response
* errors
* limits
* examples

---

# 82. Generated Types

Where possible, generate TypeScript API types from OpenAPI.

This avoids frontend/backend model drift.

---

# 83. API Compatibility

Breaking changes must not silently alter existing responses.

For example, do not change:

```json
"type": "word"
```

to:

```json
"type": "lexeme"
```

without versioning or compatibility handling.

---

# 84. Graph API Contract Tests

The frontend should have contract tests ensuring:

```text

     ↓
Expected schema
```

This prevents backend refactoring from unexpectedly breaking the graph UI.

---

# 85. Security

The API must protect against:

* SQL injection
* Cypher injection
* parameter injection
* denial-of-service through expensive traversal
* oversized responses
* rate abuse

Never expose raw Cypher or SQL execution to the client.

# 94. Response Size Protection

Even valid graph queries may produce huge responses.


# 95. Partial Responses

If a graph hits the maximum limit:

Do not fail the request completely.

Return:

```json
{
  "nodes": [],
  "edges": [],
  "meta": {
    "truncated": true,
    "reason": "NODE_LIMIT"
  }
}
```

The frontend can show:

```text
Graph truncated — expand selectively
```

---

# 96. Graph Traversal Metadata

Every graph response should include:

```json
{
  "meta": {
    "root": "uuid",
    "depthRequested": 4,
    "depthReturned": 4,
    "nodesReturned": 37,
    "edgesReturned": 42,
    "truncated": false
  }
}
```

This is useful for debugging and UX.

# 99. Cache Stampede Protection

If many users request the same uncached graph simultaneously:

```text
100 requests
     ↓
100 database queries
```

should be avoided.

Use request coalescing or locking where justified.

---

# 100. Backend Deployment

The application should be deployable as a stateless API.

```text
           Load Balancer
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
     API 1     API 2     API 3
       │         │         │
       └─────────┼─────────┘
                 ▼
             PostgreSQL
```

Application instances should not depend on local mutable state.

---

# 101. Statelessness

Avoid storing important state in application memory.

Good:

```text
database
Redis
client
```

Bad:

```text
server memory = source of truth
```

---

# 109. Important Architectural Rule

Do **not** let the React application dictate the database query.

Bad architecture:

```text

 ↓
custom Cypher
 ↓
database
```

Correct:

```text

 ↓
API contract
 ↓
Graph Service
 ↓
Repository
 ↓
Database
```

# 110. Optimization Priority

Optimization should follow this order:

### Priority 1 — Correctness

The graph must be semantically correct.

### Priority 2 — Query Safety

Bound depth, nodes, edges, and execution time.

### Priority 3 — Database Performance

Indexes and query optimization.

### Priority 4 — API Performance

Serialization, compression, caching.

### Priority 5 — Infrastructure Scaling

Replication, horizontal scaling, etc.

Do not reverse this order.

---

```text
Kafka
```

unless actual measurements justify them.

For LexGraph's current stage, **a well-designed PostgreSQL + AGE backend is likely sufficient**.

# 115. Definition of Done

Phase 7 is complete when the LexGraph backend is no longer merely an API that **happens to query a graph**.

It should function as a proper **Graph Application Platform**:

```text
                 ┌─────────────────────┐
                 │      Web Client      │
                 └──────────┬──────────┘
                            │
                            ▼
                 ┌─────────────────────┐
                 │     Versioned API   │
                 └──────────┬──────────┘
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
        Search Service  Knowledge       Graph
                         Service        Service
             │              │              │
             └──────────────┼──────────────┘
                            ▼
                  ┌──────────────────┐
                  │ Cache / Read Path│
                  └────────┬─────────┘
                           ▼
                  ┌──────────────────┐
                  │ PostgreSQL + AGE │
                  └──────────────────┘
```

The key outcome is **predictability**.

A request such as:

```text
"Give me the ancestors of this word up to depth 4"
```

must have:

* a known API contract,
* a bounded computational cost,
* predictable response size,
* measurable latency,
* safe database behavior,
* clear semantics,
* consistent error handling,
* and enough observability to diagnose problems.

That foundation is what allows the later LexGraph phases—advanced graph UX, analytics, recommendations, and eventually AI features—to build on the system without turning the backend into a bottleneck.
