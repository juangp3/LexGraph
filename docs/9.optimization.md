# Phase 9 — Performance, Scalability & Observability

## 1. Objective

Make LexGraph capable of moving from a prototype into a production-grade web application without performance degradation as the number of:

* words
* languages
* meanings
* relationships
* sources
* graph traversals
* concurrent users

increases.

This phase has three pillars:

```text
                 Phase 9
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   Performance   Scalability  Observability
        │           │           │
      Fast        Growth       Know why
      queries     capacity     something is slow
```

The objective is **not** to prematurely distribute the system across many services.

The architecture should first become measurable, predictable, and efficient on a relatively simple deployment.

# 3. Non-Goals

Do **not** introduce unnecessary infrastructure simply because the application may eventually become large.

Phase 9 should **not automatically introduce**:

* Kubernetes
* microservices
* Kafka
* Redis clusters
* multiple databases
* service mesh
* event-driven architecture everywhere
* distributed graph databases
* CDN architecture beyond actual need

The default principle is:

> **Optimize the current architecture before adding architectural complexity.**

# 5. Performance Philosophy

Performance should be treated as a measurable engineering property.

Do not optimize based on:

> "This endpoint feels slow."

Instead:

```text
Request
   ↓
Measure
   ↓
Identify bottleneck
   ↓
Optimize
   ↓
Benchmark
   ↓
Compare
```

---

# 6. Service-Level Performance Targets

Initial targets should be defined for the production API.

These are **initial engineering targets**, not promises to users.

| Operation      | Target p50 | Target p95 | Target p99 |
| -------------- | ---------: | ---------: | ---------: |
| Health check   |      <20ms |      <50ms |     <100ms |
| Word lookup    |     <100ms |     <250ms |     <500ms |
| Search         |     <150ms |     <400ms |     <800ms |
| Word inspector |     <200ms |     <500ms |        <1s |
| Graph depth 1  |     <200ms |     <500ms |        <1s |
| Graph depth 2  |     <400ms |        <1s |        <2s |
| Graph depth 3  |     <750ms |        <2s |        <4s |

These numbers should be validated against the actual infrastructure.

---

# 7. Why Percentiles Matter

Average latency is insufficient.

Example:

```text
99 requests = 100ms
1 request  = 10 seconds
```

Average:

```text
199ms
```

That looks acceptable.

But one user experienced a 10-second request.

Therefore LexGraph should monitor:

```text
p50
p90
p95
p99
```

At minimum.

---

# 8. API Latency Budget

Every request should have an approximate budget:

```text
HTTP request
   │
   ├── validation       5ms
   ├── cache            10ms
   ├── database         100ms
   ├── transformation   30ms
   └── serialization    20ms
                         ─────
                         165ms
```

This makes bottlenecks visible.

---

# 9. Database Performance

The database is likely to become one of the most important performance constraints.

Primary concerns:

* missing indexes
* inefficient joins
* graph traversal
* large result sets
* duplicate queries
* excessive ORM queries
* sequential scans
* expensive sorting
* connection exhaustion

---

# 10. Database Query Monitoring

Every important query pattern should be measurable.

Track:

```text
query count
execution time
rows scanned
rows returned
index usage
```

The goal is to identify queries such as:

```text
10ms → good
150ms → investigate
2s → unacceptable
10s → critical
```

---

# 11. Index Strategy

Indexes should exist for common access patterns.

Potential indexes:

```text
entities.id
entities.type
entities.normalized_text
entities.language_id

relationships.source_entity_id
relationships.target_entity_id
relationships.type

languages.iso_code

sources.id
```

Exact indexes must be based on actual queries.

Do not create indexes blindly.

---

# 12. Composite Indexes

Where queries commonly combine fields, consider composite indexes.

Example:

```text
language_id + normalized_text
```

instead of:

```text
language_id
normalized_text
```

if the dominant query is:

```sql
WHERE language_id = ?
AND normalized_text = ?
```

Validate using query plans.

---

# 13. Query Plan Analysis

Important queries must be analyzed with the database query planner.

Look for:

```text
Sequential Scan
Nested Loop
Large Sort
Large Hash
Excessive Rows Removed
```

The goal is not:

> "Use indexes everywhere."

The goal is:

> "Use the cheapest execution plan for the actual workload."

---

# 14. N+1 Query Prevention

The API must avoid:

```text
Get word
 ↓
Get language
 ↓
Get meaning
 ↓
Get source
 ↓
Get source
 ↓
Get source
```

for every item.

Instead, use:

* joins
* batching
* eager loading
* explicit repository queries
* data loaders where appropriate

---

# 15. Graph Query Optimization

Graph queries are likely to be the most expensive operations.

The API must enforce:

```text
maximum depth
maximum nodes
maximum edges
maximum execution time
```

Example:

```text
depth <= 4
nodes <= 500
edges <= 1000
```

These should be configurable.

---

# 16. Graph Traversal Explosion

Avoid:

```text
depth 1 → 20 nodes
depth 2 → 500 nodes
depth 3 → 15,000 nodes
depth 4 → 400,000 nodes
```

A user's graph request must never be allowed to consume uncontrolled resources.

---

# 17. Graph Query Budget

Each graph request should have a computational budget.

Conceptually:

```text
Graph request
   │
   ├── depth budget
   ├── node budget
   ├── edge budget
   └── execution-time budget
```

If exceeded:

```json
{
  "truncated": true,
  "reason": "NODE_LIMIT"
}
```

---

# 18. Partial Graph Responses

A graph response can legitimately be incomplete.

Example:

```json
{
  "nodes": [...],
  "edges": [...],
  "meta": {
    "truncated": true,
    "totalAvailable": 1423,
    "returned": 250
  }
}
```

The frontend should be able to communicate:

> Showing 250 of 1,423 relationships.

---

# 19. Pagination

Never return arbitrarily large collections.

Pagination is required for:

* search
* sources
* meanings
* cognates
* descendants
* language members
* graph expansions

Use cursor pagination where appropriate.

---

# 20. Cursor Pagination

Prefer:

```text
?cursor=abc123&limit=50
```

over:

```text
?page=500
```

for large datasets.

Cursor pagination avoids increasingly expensive offsets.

---

# 21. Pagination Limits

Define:

```text
defaultLimit = 20
maximumLimit = 100
```

Exact values can be tuned.

Clients should not be allowed to request:

```text
limit=1000000
```

---

# 22. Search Performance

Search is a high-frequency operation.

It should support:

* exact match
* prefix search
* normalized search
* language filtering
* relevance ranking

Avoid database patterns such as:

```sql
LIKE '%father%'
```

on millions of records unless the database/index strategy explicitly supports it.

---

# 23. Search Index

If the dataset becomes large, introduce a dedicated search index.

Potential options:

```text
PostgreSQL full-text search
OpenSearch
Elasticsearch
Meilisearch
Typesense
```

Do not introduce one simply because it is popular.

Start with the simplest technology that meets the measured requirements.

---

# 24. Search Architecture

Recommended evolution:

### Stage 1

```text
API
 ↓
PostgreSQL
```

### Stage 2

```text
API
 ↓
Search Index
 ↓
PostgreSQL
```

Search index returns candidate IDs.

Database provides authoritative entity details.

---

# 25. Cache Strategy

Caching should be introduced around expensive and frequently repeated operations.

Potential cache candidates:

```text
word lookup
language lookup
popular searches
graph queries
language-family trees
```

---

# 26. Cache Layers

Potential architecture:

```text
Browser cache
      ↓
Next.js cache
      ↓
API cache
      ↓
Database
```

Do not cache everything.

---

# 27. Cache Key Design

Keys must uniquely identify query parameters.

Example:

```text
word:v1:{wordId}
```

Graph:

```text
graph:v1:{entityId}:{type}:{depth}:{filters}
```

Search:

```text
search:v1:{normalizedQuery}:{language}:{page}
```

---

# 28. Cache Invalidation

The hardest part of caching is invalidation.

When a relationship changes:

```text
word
  ↓
graph cache
  ↓
search cache
```

may become stale.

Therefore:

> Prefer short TTLs and explicit invalidation only where necessary.

---

# 29. Cache TTL

Example starting values:

```text
Word detail: 5–30 min
Language metadata: hours
Graph queries: 5–30 min
Search results: 1–10 min
Static metadata: hours/days
```

Tune based on actual update frequency.

---

# 30. Cache Stampede Prevention

If an expensive cache expires and 1,000 requests arrive simultaneously:

```text
1000 requests
      ↓
database
      ↓
💥
```

Use request coalescing / single-flight behavior where practical.

---

# 31. HTTP Caching

Use appropriate headers:

```text
Cache-Control
ETag
Last-Modified
```

where useful.

This can reduce API traffic without introducing additional infrastructure.

---

# 32. Frontend Performance

The web application should meet modern web performance expectations.

Track:

* LCP
* INP
* CLS
* TTFB

and page-specific metrics.

---

# 33. Core Web Vitals

Target:

```text
LCP: good
INP: good
CLS: good
```

The exact thresholds should follow current Google Core Web Vitals guidance rather than hard-coding outdated values.

---

# 34. Next.js Optimization

Use:

* server components where appropriate
* dynamic imports
* route-level code splitting
* image optimization
* streaming where useful
* static rendering for stable content
* caching for stable API responses

Do not make everything client-side by default.

---

# 35. Graph Rendering Performance

React Flow can become expensive with many nodes.

The frontend must:

* limit rendered nodes
* avoid unnecessary re-renders
* memoize node components
* virtualize where appropriate
* avoid rendering invisible elements unnecessarily
* debounce expensive interactions

---

# 36. Graph Layout Performance

Automatic layout can become a bottleneck.

The system should:

```text
API graph
   ↓
layout algorithm
   ↓
positions
   ↓
render
```

rather than recalculating the entire layout on every interaction.

---

# 37. Layout Strategy

For the initial system:

```text
small graph → client-side layout
large graph → constrained layout
very large graph → server/precomputed layout
```

Do not automatically calculate thousands of nodes in the browser.

---

# 38. Debouncing

Search input should be debounced.

Example:

```text
f
fa
fat
fath
fathe
father
```

should not necessarily generate six API requests.

Use approximately:

```text
200–300ms
```

as a starting point.

Tune based on UX and API behavior.

---

# 39. Request Cancellation

If the user searches:

```text
father
```

then immediately:

```text
fathers
```

the older request should be cancelled or ignored.

Otherwise stale results can overwrite newer results.

---

# 40. API Connection Management

Database connections must be bounded.

Define:

```text
maximum connections
minimum connections
connection timeout
idle timeout
query timeout
```

Avoid creating a new database connection per request.

---

# 41. Connection Pooling

Architecture:

```text
API instances
   │
   ├── connection
   ├── connection
   └── connection
        ↓
   connection pool
        ↓
     database
```

If deployment scales horizontally, database connection limits must be considered globally.

---

# 42. Query Timeout

Every expensive query should have a maximum execution time.

Example:

```text
normal query: 1–2 seconds maximum
graph query: configurable
```

The application must fail gracefully rather than allow runaway queries.

---

# 43. API Rate Limiting

Public API endpoints require rate limiting.

Potential policy:

```text
Anonymous:
60 requests/minute

Authenticated:
higher limit

Admin:
special policy
```

These are starting values, not fixed requirements.

---

# 44. Endpoint-Specific Limits

Graph requests should have stricter limits than:

```text
GET /words/{id}
```

because they are computationally more expensive.

Example:

```text
search: 120/min
word detail: 120/min
graph: 30/min
large graph: 10/min
```

---

# 45. Abuse Protection

Protect against:

* repeated expensive graph queries
* huge pagination requests
* search flooding
* malformed requests
* concurrent expensive requests

---

# 46. Concurrency Control

Limit simultaneous expensive operations per client.

Example:

```text
maximum concurrent graph requests = 2
```

This prevents a single user from consuming all available resources.

---

# 47. Background Jobs

Heavy operations should not run synchronously.

Potential candidates:

* data ingestion
* graph rebuilding
* search index updates
* statistics
* data validation
* large imports
* cache warming

Architecture:

```text
API
 ↓
Job Queue
 ↓
Worker
 ↓
Database / Search Index
```

---

# 48. Job Requirements

Every background job should have:

```text
job ID
status
createdAt
startedAt
finishedAt
attempts
error
```

Example:

```json
{
  "id": "...",
  "status": "RUNNING",
  "attempts": 1
}
```

---

# 49. Retry Strategy

Jobs should support controlled retries.

Example:

```text
attempt 1
   ↓
failure
   ↓
backoff
   ↓
attempt 2
   ↓
failure
   ↓
attempt 3
   ↓
dead-letter / failed
```

Avoid infinite retries.

---

# 50. Idempotency

Jobs such as:

```text
Import source dataset
Build graph relationships
Update search index
```

must be idempotent where possible.

Running the same job twice should not create duplicate entities or relationships.

---

# 51. Horizontal Scalability

The API should ideally be stateless.

Architecture:

```text
                 Load Balancer
                 /     |     \
                /      |      \
             API 1    API 2    API 3
                \       |       /
                 \      |      /
                  Database
```

Any API instance should be capable of handling any request.

---

# 52. Stateless API

Do not store critical session state only in memory.

Avoid:

```text
API 1 memory:
user state

API 2:
doesn't know it
```

Use:

* signed tokens
* database
* shared cache
* external session store

where necessary.

---

# 53. Autoscaling

If deployment supports it, scale API instances based on:

* CPU
* memory
* request rate
* latency
* concurrency

But autoscaling should only be introduced after measuring actual workload.

---

# 54. Database Scaling

The database is likely to become the primary scaling constraint.

Potential progression:

```text
Single PostgreSQL
       ↓
Optimized PostgreSQL
       ↓
Connection pooling
       ↓
Read replicas
       ↓
Partitioning
       ↓
Specialized systems
```

Do not skip directly to distributed databases.

---

# 55. Read Replicas

If LexGraph becomes read-heavy:

```text
                API
                 │
       ┌─────────┴─────────┐
       ▼                   ▼
   Primary             Replica
   writes              reads
```

But consistency requirements must be understood first.

---

# 56. Eventual Consistency

Search indexes and caches may temporarily lag behind the primary database.

Example:

```text
Database updated
      ↓
Search index
      ↓
30 seconds later
```

This is acceptable if explicitly designed.

The primary database remains authoritative.

---

# 57. Availability

Define an initial target.

Example:

```text
99.5% monthly API availability
```

Later:

```text
99.9%
```

Do not target 99.99% before the product actually requires it.

---

# 58. Health Checks

Implement:

```text
GET /health
```

for basic process health.

And:

```text
GET /ready
```

for readiness.

---

# 59. Health vs Readiness

Health:

> Is the application process alive?

Readiness:

> Can this instance actually serve requests?

For example:

```text
Database unavailable
```

may mean:

```text
health = OK
readiness = FAIL
```

depending on architecture.

---

# 60. Dependency Health

Monitor dependencies:

```text
Database
Search index
Cache
Queue
External APIs
```

But do not make the health endpoint perform expensive checks.

---

# 61. Structured Logging

Logs should be machine-readable.

Example:

```json
{
  "timestamp": "...",
  "level": "INFO",
  "service": "lexgraph-api",
  "requestId": "...",
  "route": "/v1/graph/123",
  "durationMs": 243,
  "status": 200
}
```

Avoid unstructured messages such as:

```text
Graph request worked!!
```

---

# 62. Request ID

Every request should receive:

```text
requestId
```

Example:

```text
req_01JXYZ...
```

The same ID should appear in:

* API logs
* database-related logs where useful
* error reports
* traces

---

# 63. Correlation ID

For distributed operations:

```text
HTTP request
   ↓
job
   ↓
worker
   ↓
database
```

maintain correlation.

This allows debugging an operation across components.

---

# 64. Log Levels

Use:

```text

ERROR
```

# 65. Sensitive Data

* tokens
* private credentials
* unnecessary personal information

# 81. Alerts

Alerts should be based on symptoms rather than every small fluctuation.

Examples:

### Critical

```text
API error rate > 5%
Database unavailable
API p95 > 5s
```

### Warning

```text
API p95 > 1s
Cache hit ratio < expected
Database connections > 80%
```

Exact thresholds should be calibrated using real traffic.

---

# 82. Alert Fatigue

Avoid:

```text
Alert every time latency rises 5%.
```

This creates noise.

Use sustained conditions:

```text
p95 > threshold for 5 minutes
```

or similar policies.

---

# 83. SLOs

Example:


# 84. Error Budget

# 129. Definition of Done

Phase 9 is complete when LexGraph can answer these questions **with actual measurements rather than assumptions**:

> How fast is a word lookup?

> How fast is search at p95?

> How fast is a graph traversal at depth 1, 2 and 3?

> What happens when 100 users search simultaneously?

> What happens when 100 users open graphs simultaneously?

> What is the maximum graph size the frontend can render reliably?

> Which database query is currently the bottleneck?

> What happens when the database becomes slow?

> What happens when the search service is unavailable?

> How much traffic can the current deployment handle?

> When do we need another API instance?

> When do we need a search engine?

> When do we need a read replica?

> How do we know a new release made performance worse?

> If a user reports a failed graph request, can we trace exactly what happened?

The strongest version of Phase 9 is therefore **not "make LexGraph fast."**

It is:

```text
                MEASURE
                   ↓
              UNDERSTAND
                   ↓
               OPTIMIZE
                   ↓
               BENCHMARK
                   ↓
               MONITOR
                   ↓
                SCALE
```

That gives LexGraph a controlled path from the current prototype toward a production system without prematurely introducing distributed-system complexity.
