# Phase 10 — User Features & Workspace Management

## 1. Objective

Transform LexGraph from a primarily **public knowledge-exploration application** into a product where users can build and maintain their own personal research space.

The core idea is:

> A user should not only be able to discover an etymological relationship; they should be able to **save it, organize it, revisit it, annotate it, and build a personal collection of linguistic knowledge.**

This phase introduces the user/workspace layer without turning LexGraph into a social network or collaborative platform.

The target experience is:

```text
Discover
   ↓
Inspect
   ↓
Save
   ↓
Organize
   ↓
Annotate
   ↓
Revisit
   ↓
Explore further
```

---

# 3. Non-Goals

This phase should **not** introduce:

* public social profiles
* followers
* likes
* comments between users
* messaging
* collaborative editing
* public user-generated dictionaries
* reputation systems
* social feeds
* complex permissions
* enterprise organizations

Those can be considered later if the product direction justifies them.

The initial model should remain:

> **LexGraph knowledge is public; a user's workspace is private.**

---

# 4. Product Model

There are two fundamentally different types of information.

### LexGraph knowledge

```text
Word
Language
Meaning
Relationship
Etymology
Source
Language family
```

This belongs to LexGraph.

### User workspace

```text
Saved Word
Saved Graph
Collection
Note
Bookmark
History
Preference
```

This belongs to the user.

The architecture should keep these concepts separate.

# 6. User Experience

A typical workflow:

```text
User searches "father"
        ↓
Finds English "father"
        ↓
Opens Word Inspector
        ↓
Explores graph
        ↓
Finds Proto-Indo-European ancestor
        ↓
Clicks "Save"
        ↓
Selects collection:
"Linguistics Research"
        ↓
Adds note:
"Interesting relationship..."
        ↓
Later opens Workspace
        ↓
Continues exploration
```

This should feel like a **research notebook for language**.

# 7. Authentication

Users must be able to create an account and authenticate securely.

Possible authentication providers:

* Email/password
* Google
* GitHub
* Apple

The first implementation should minimize complexity.

Recommended initial approach:

```text
Authentication provider
        ↓
LexGraph user identity
        ↓
Workspace
```

Authentication should preferably be delegated to a mature authentication framework/provider rather than implemented from scratch.

---

# 8. Anonymous Users

Users should be able to use the core LexGraph experience without creating an account.

Anonymous users can:

* search
* inspect words
* explore graphs
* browse languages
* view sources

But persistent workspace features require authentication:

```text
Save
Collections
Notes
History synchronization
Preferences synchronization
```

---

# 9. Anonymous → Authenticated Transition

If an anonymous user clicks:

> Save Word

show:

```text
Save this word to your workspace

[ Sign in ]
[ Create account ]
```

After authentication, return the user to the original action.

Example:

```text
Search
 ↓
Word
 ↓
Save
 ↓
Login
 ↓
Word is saved
```

The user should not have to repeat the action.


The user ID must never change because the user changes:

* email

# 14. Workspace

Each user gets one primary workspace.

```text
User
 │
 └── Workspace
       ├── Saved Words
       ├── Saved Graphs
       ├── Collections
       ├── Notes
       └── History
```

A workspace does not necessarily need to be a separate database entity initially.

It can be logically represented by:

```text
userId
```

on user-owned records.

However, introducing a `workspace` abstraction in the domain model may make future multi-workspace support easier.

# 18. Saved Word Data Model

Conceptually:

```text
SavedWord
---------
id
userId
wordId
createdAt
collectionId?
```

Important:

> Do not duplicate the LexGraph word itself.

The saved record should reference the canonical LexGraph entity.

---

# 19. Prevent Duplicate Saves

A user should not be able to save the same word multiple times unintentionally.

Database constraint:

```text
UNIQUE(userId, wordId)
```

unless multiple collection memberships are modeled separately.

---

# 20. Multiple Collections

A saved word may belong to multiple collections.

Avoid:

```text
SavedWord.collectionId
```

if multi-collection membership is desired.

Instead:

```text
SavedWord
     │
     ▼
CollectionMembership
     │
     ▼
Collection
```

Conceptually:

```text
User
 │
 ├── SavedWord A
 │       ├── Collection X
 │       └── Collection Y
 │
 └── SavedWord B
         └── Collection X
```

---

# 24. Collection Deletion

Deleting a collection should **not delete the underlying saved words**.

Example:

```text

```

# 25. Saved Graphs

Graphs deserve a separate saved-object type.

A user might find a graph particularly interesting:

```text
father
  ↓
Old English fæder
  ↓
Proto-Germanic
  ↓
PIE *ph₂tḗr
```

They should be able to save the exploration.

---

# 26. Saved Graph Model

Potential model:

```text
SavedGraph
----------
id
userId
rootEntityId
title
depth
filters
createdAt
updatedAt
```

Important:

> Do not necessarily store the entire graph snapshot initially.

Store the parameters required to reproduce it.

---

# 27. Graph Snapshot vs Graph Query

There are two approaches.

### Query-based

```text
root = father
depth = 3
filters = [...]
```

Advantages:

* always reflects latest data
* very small storage

Disadvantage:

* graph may change over time

### Snapshot-based

Store:

```text
nodes
edges
metadata
```

Advantages:

* historical preservation

Disadvantages:

* much larger
* stale
* harder to maintain

---

# 28. Recommended Approach

Use **query-based saved graphs initially**.

Allow future snapshots if users need historical research preservation.

---

* in other users' workspaces
* in search engines

Example:



Conceptually:

```text

```

If the user views the same entity again:

```text

```

rather than creating unlimited duplicates.

# 42. Recent View Limit

Keep only a fixed number:

```text

```

This keeps the dataset small.

# 44. Do Not Overbuild Preferences

Avoid storing UI state that can remain local.

For example:


# 55. Workspace API

The backend should expose dedicated workspace endpoints.

Potential structure:

```text
/v1/me
/v1/me/preferences

/v1/me/saved-words
/v1/me/saved-graphs

/v1/me/collections
/v1/me/collections/{id}

/v1/me/notes
/v1/me/history
/v1/me/recent

/v1/me/export
/v1/me/import
```

---

# 56. `/me` Principle

Never require the frontend to send:

```text
/user/{userId}/...
```

for normal authenticated operations.

Use:

```text
/v1/me/...
```

The authenticated identity comes from the authentication context.

This reduces authorization mistakes.

---

# 57. Authorization

Every workspace query must enforce:

```text
authenticatedUser.id == resource.userId
```

Server-side.

Never rely on the frontend to enforce ownership.

---

# 58. Critical Security Rule

This must **never** be sufficient:

```text
GET /notes/{noteId}
```

where the server simply retrieves the note.

It must verify:

```text
note.userId == authenticatedUser.id
```

Otherwise users could potentially access another user's notes by guessing IDs.

---

# 59. ID Security

Use opaque identifiers such as UUIDs.

But remember:

> UUIDs are not an authorization mechanism.

Authorization must still be enforced.

---

# 61. Database Relationships

Conceptually:

```text

 │
 ├────< SavedWord >──── Word
 │
 ├────< SavedGraph >─── Word

 ├────< Collection
 │           │
```

# 62. Foreign Keys

User-owned data should have appropriate foreign keys.

For example:

```text
saved_words.user_id → users.id
saved_words.word_id → words.id
notes.user_id → users.id
collections.user_id → users.id
```

---

# 63. Cascading Deletes

Carefully define deletion behavior.

Deleting a user should eventually remove or anonymize:

```text
saved words
saved graphs
collections
notes
history
preferences
```

while **never deleting the underlying public LexGraph knowledge**.

---

# 64. Account Deletion

User should be able to request:

> Delete my account.

The operation should be explicit and destructive.

Suggested flow:

```text
Settings
 ↓
Delete account
 ↓
Warning
 ↓
Confirm
 ↓
Re-authenticate if necessary
 ↓
Delete/anonymize
```

---

# 65. Account Deletion Policy

Define whether deletion is:

### Hard delete

Remove all user-owned data.

or:

### Soft delete

Mark account:

```text
DELETED
```

and remove/anonymize personal information.

The implementation must follow the applicable privacy/legal requirements.

---

# 66. Email Change

If email/password authentication is used:

Changing email should require appropriate verification.

Do not simply allow:

```text
PUT /me
email = attacker@example.com
```

without verification.

---

# 67. Authentication Security

Implement:

* secure sessions
* secure cookies where applicable
* CSRF protection where relevant
* rate limiting
* authentication event logging
* secure password handling if passwords are managed directly

Prefer an established authentication solution.



---

# 86. Workspace Sorting

Support useful sorting:

```text

Alphabetical
Language

Updated
```

---

# 87. Workspace Search Performance

Workspace search should be significantly simpler than global linguistic search.

For moderate user datasets:

```text
PostgreSQL
```

should be sufficient.

Do not introduce a dedicated search engine for private workspaces unless usage demonstrates the need.

---

# 88. Caching User Data

Be extremely careful with caching authenticated responses.

Cache keys must include user identity.

Never allow:

```text
User A workspace
      ↓
shared cache
      ↓
User B receives it
```

This is a **critical security concern**.

---

# 89. Authorization Testing

Create tests specifically for:

```text
User A cannot read User B's saved words
User A cannot modify User B's collections
User A cannot read User B's notes
User A cannot delete User B's graph
```

These are mandatory security tests.

---

# 91. Idempotency

Actions should be safe where appropriate.

Example:

```text
POST save father
POST save father
```

should not create duplicate saved records.

Likewise:

```text
DELETE saved father
DELETE saved father
```

should not produce unexpected behavior.

* authenticated access
* authorization
* short-lived download mechanism if applicable
* no public indexing
* audit logging where appropriate

---

# 95. Import Security

Never blindly trust imported content.

Validate:

* size
* schema
* strings
* references
* nesting
* number of objects

Protect against maliciously huge imports.

---

# 96. Maximum Workspace Size

Define reasonable limits.

Example starting values:

```text
Saved words: 50,000
Saved graphs: 5,000
Collections: 100
Notes: 50,000
History entries: 500
```

These are protection limits, not intended user targets.

---

# 97. Large Workspace Handling

If a user eventually has:

```text
50,000 saved words
```

the application must not load them all.

Always:

```text
paginate
filter
search
virtualize
```

where necessary.

For example, prefer:


# 103. Telemetry Privacy

# 141. Final Product Principle

The most important design decision for Phase 10 is to avoid turning LexGraph into a generic bookmarking application.

The workspace should reinforce what makes LexGraph unique:

> **Users are building their own map of linguistic knowledge.**

Therefore the strongest long-term experience is:

```text
              LEXGRAPH
                  │
        ┌─────────┴─────────┐
        │                   │
    Knowledge           My Workspace
        │                   │
        ▼                   ▼
   Explore graph       Save discoveries
   Inspect words       Organize collections
   Follow ancestry     Write notes
   Compare languages   Build research trails
        │                   │
        └─────────┬─────────┘
                  ▼
          Personal Knowledge Map
```

That distinction should guide the implementation: **the public graph is the knowledge engine; the workspace is the user's persistent relationship with that graph.**
